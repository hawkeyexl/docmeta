---
title: Roll out a new required field without breaking the build
description: Make a metadata field required today, record the existing backlog as a baseline so the build stays green, and let the debt shrink from there.
---

import { Steps, Aside, LinkCard, CardGrid } from '@astrojs/starlight/components';

Your metadata standard needs to grow. Maybe you want every doc to carry an `owner`, or you decided `description` should be mandatory rather than recommended. The risk is obvious: flip a field to required in one commit and the next CI run fails on every existing doc that predates the rule. On a large repo that is hundreds of red checks at once, and no contributor can merge until the backlog is cleared.

A **baseline** removes that trade-off. You record today's violations once, and from then on docmeta fails only on findings that are *new*. The rule is live immediately for everything anyone writes from now on, and the backlog stays visible instead of blocking the build.

<Aside type="note" title="Why this works">
A baseline is a file of violation fingerprints, keyed by document path. On each run docmeta fingerprints the findings it sees and subtracts the ones already recorded. A recorded violation is forgiven; anything else fails the run. Nothing about the schema is relaxed, so a new doc that omits the field fails on the pull request that adds it.
</Aside>

This guide assumes you already have a working `docmeta.config.yaml` and a schema you control. If you are still using the built-in OKF schema, [author your own schema first](/docmeta/schemas/) so you have a file to edit; you cannot add fields to a built-in.

## Step 1: Add the field as required

Add the new field to your schema's `properties` **and** to `required`. No staging, no second lenient copy of the schema to keep in sync.

```json title="schemas/doc.json" {4,10-13}
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["type", "owner"],
  "properties": {
    "type": {
      "type": "string",
      "minLength": 1
    },
    "owner": {
      "type": "string",
      "minLength": 1
    }
  }
}
```

Run a pass to see the size of the backlog you are about to record:

```bash
npx docmeta validate
```

That run exits `1` and lists every doc missing `owner`. This is the wall of red the baseline exists to absorb — read it once, so you know what you are agreeing to forgive.

## Step 2: Record the backlog

```bash
npx docmeta validate --write-baseline
```

```
Baseline written to .docmeta-baseline.json
  412 findings recorded (+412 new, -0 no longer occur)
```

Commit `.docmeta-baseline.json` alongside the schema change. It is a source file: reviewers should see it grow or shrink in the diff, and a pull request that adds entries is a pull request that added violations.

<Aside type="caution" title="Read the two numbers, every time">
`--write-baseline` replaces the file with what *this run* saw. If a narrowed glob or a mistyped `--exclude` means the run saw fewer files than you intended, the entries it did not see are silently forgiven — and `-N no longer occur` is the only thing that says so. A re-record that reports large `-N` you cannot explain should not be committed.
</Aside>

## Step 3: Turn the baseline on

Point your config at the file so every run — yours and CI's — compares against it:

```yaml title="docmeta.config.yaml"
paths:
  - "docs/**/*.md"

schemas:
  - ./schemas/doc.json

baseline: .docmeta-baseline.json
```

```bash
npx docmeta validate
```

```
✓ docs/api/legacy.md  (2 baselined)
✓ docs/guides/intro.md

2 files checked, 2 passed, 0 failed, 0 errors
412 baselined findings
```

Green build, live rule. Ship it.

<Aside type="tip" title="The path is relative to the config file">
`baseline:` resolves against the directory holding `docmeta.config.yaml`, not against wherever you happened to run the command. Running `docmeta validate` from a subdirectory finds the same baseline CI does.
</Aside>

## Step 4: Watch the debt shrink

<Steps>

1. **New violations fail immediately.** A doc that lands without `owner` produces a fingerprint that is not in the baseline, so the run exits `1` and names only that file. The rule you shipped in step 1 is doing its job from day one.

2. **Fixed violations are reported, not forgotten.** When someone adds the missing field, its fingerprint stops occurring and the summary says so:

   ```
   412 baselined findings, 37 no longer occur — run --write-baseline to prune
   ```

3. **Prune when the number gets noisy.** Re-record to drop the entries that no longer apply:

   ```bash
   npx docmeta validate --write-baseline
   ```

   ```
   Baseline written to .docmeta-baseline.json
     375 findings recorded (+0 new, -37 no longer occur)
   ```

   The count in the summary is the debt, on every run. When it reaches zero, delete the file and drop the `baseline:` key — the ratchet is finished.

</Steps>

<Aside type="tip" title="Closing the backlog faster">
The baseline makes the backlog safe to carry, not smaller. To actually work it down, [`docmeta fill`](/docmeta/reference/cli/#fill) infers the missing values from each page's content and writes back the ones it is confident about — and because the schema drives the prompt, the fields it proposes are exactly the ones you just made required.
</Aside>

## Two things a baseline does not forgive

- **A renamed file.** Entries are keyed by path, so moving a document takes its findings to a key with no entry and every one of them reads as new. The fix is one `--write-baseline`; the stale-entry line in the summary is the hint that a rename, not a regression, is what happened.
- **A re-pointed schema.** The schema reference is part of a violation's identity, so switching `./schemas/doc.json` to a URL serving identical bytes changes every fingerprint. Re-record when you move a schema.

<Aside type="caution" title="A file with no frontmatter still gets checked">
A required-field rule flags **every** non-compliant file, including files with no frontmatter block at all — a blank doc has no `owner` any more than a doc that simply omits it. These are recorded in the baseline like anything else, so they will not surprise the build; just do not read a green run as evidence that they have frontmatter.
</Aside>

## What you have now

A required field that went live the day you wrote it, a build that stayed green, and a single file that says exactly how much legacy debt is left — visible on every run, shrinking as contributors touch their pages. No parallel lenient schema, no hand-maintained list of which folders are clean, nothing to keep in sync.
