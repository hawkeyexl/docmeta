Real docs repos are not uniform. Your `/api` reference pages might need a `type: api-reference` field and an extra schema, while your `/guides` only need the baseline. docmeta handles this with **overrides** in your `docmeta.config.yaml`. Each override maps a glob of files to its own schema set. So you can tighten the rules for one area without touching the rest.

This guide assumes you already have a working config. If not, start with [Create your docmeta.config.yaml](/docmeta/set-up/config/).

## Assign a schema set per area

An `overrides` entry pairs a `files` glob with a `schemas` list. Any file matching the glob is validated against that override's schemas instead of the default `schemas`.

```yaml title="docmeta.config.yaml"
# The baseline every doc must satisfy.
schemas:
  - google:okf:0.1

# Area-specific rules.
overrides:
  - files: "api/**/*.md"
    schemas:
      - ./schemas/api-reference.json
  - files: "guides/**/*.md"
    schemas:
      - ./schemas/guide.json
```

With this config:

- Files under `api/` are validated against `./schemas/api-reference.json`.
- Files under `guides/` are validated against `./schemas/guide.json`.
- Everything else falls back to the default `schemas`: here, `google:okf:0.1`.

<Aside type="note">
An override **replaces** the default `schemas` for matching files; it does not add to them. If you want an area to satisfy the baseline *and* an extra schema, list both in that override (see [Validate one file against multiple schemas](#validate-one-file-against-multiple-schemas) below).
</Aside>

## First matching override wins

docmeta evaluates overrides **in order** and stops at the first glob that matches a given file. Order your overrides from most specific to least specific, so a narrow rule is not shadowed by a broader one above it.

```yaml title="docmeta.config.yaml"
overrides:
  # Specific first: deprecated API pages need their own schema.
  - files: "api/deprecated/**/*.md"
    schemas:
      - ./schemas/deprecated.json
  # General second: everything else under api/.
  - files: "api/**/*.md"
    schemas:
      - ./schemas/api-reference.json
```

Here, `api/deprecated/v1.md` matches the first override and is validated against `deprecated.json`. A file like `api/auth.md` falls through to the second override. If you reversed the two entries, the broad `api/**/*.md` glob would match the deprecated pages first and they would never reach their specific rule.

<Aside type="tip">
Globs match against POSIX-style paths (forward slashes), so write `api/**/*.md` even on Windows. docmeta normalizes path separators before matching.
</Aside>

## Group several globs under one schema set

Sometimes one contract governs areas that no single glob reaches. `files` accepts a list, and a file matches when **any** glob in it does:

```yaml title="docmeta.config.yaml"
overrides:
  - files:
      - ".claude/skills/*/SKILL.md"
      - ".claude/agents/*.md"
    schemas:
      - agentskills:skill:1.0
```

Reach for the list when the paths have no common stem. A per-skill `SKILL.md` one directory down, and a flat file in `.claude/agents/`, cannot be written as one brace expansion. When they *do* share a stem, either spelling works: `docs/{api,guides}/**/*.md` and the two-entry list are equivalent.

<Aside type="caution" title="Dot directories must be named to be found">
An override decides *how* a file is judged, never *whether* it is looked at. Input discovery skips dot directories: `docmeta validate .` walks past `.claude/` entirely, so the config above would match nothing at all unless the path is named as an input.

Name it in `paths:`, or pass it on the command line, and the files are found:

```yaml title="docmeta.config.yaml"
paths:
  - .claude
  - docs
```

The override globs themselves match dotfiles fine; it is only the walk that skips them. This bites hardest in exactly the case above, where every target is under a dot directory.
</Aside>

A grouped entry is still **one** override. It takes a single position in the first-match-wins order above. If you give it a `name:`, it becomes one [collection](/docmeta/reference/configuration/#named-collections), not one per glob.

## Validate one file against multiple schemas

A `schemas` list, whether the default set or an override, applies as a **set**: the file must satisfy every schema in the list. List more than one to compose rules.

```yaml title="docmeta.config.yaml"
overrides:
  - files: "api/**/*.md"
    schemas:
      - google:okf:0.1            # baseline: requires type
      - ./schemas/api-reference.json   # plus: requires the api-specific fields
```

A file under `api/` must now pass both schemas. This lets you keep the shared baseline, which is OKF's required `type`, while layering area-specific requirements on top. You avoid duplicating the baseline rules in every custom schema.

## Where overrides sit in schema resolution

Overrides are one link in docmeta's schema-resolution chain. For any single file, docmeta picks the first source that applies, in this order:

<Steps>

1. **CLI `--schema` flag**: if you pass `-s <ref>` (repeatable), it overrides everything below for the whole run.

2. **File `$schema` field**: a `$schema` key in the file's own frontmatter names its schema set and overrides the config.

3. **Config `overrides`**: the first matching override's `schemas`, as described on this page.

4. **Config `schemas`**: the default set, when no override matches.

5. **Built-in default set**: [`google:okf:0.1`](/docmeta/schemas/) plus [`passo-uno:seven-action:1.0`](/docmeta/reference/taxonomy-schemas/), when nothing else resolves.

</Steps>

So an override governs a file only when no `--schema` flag is set and the file has no `$schema` of its own. A contributor can always pin a specific file to a different schema with a `$schema` line. And you can always force a schema for a one-off run with `--schema`.

## Verify your overrides

After editing your config, confirm each area resolves to the schema set you expect. Run docmeta and read the per-file output, which reports the schemas applied to each file.

```bash
npx docmeta validate
```

If a file matches the wrong override, check the order of your `overrides` entries; remember that the first matching glob wins.
