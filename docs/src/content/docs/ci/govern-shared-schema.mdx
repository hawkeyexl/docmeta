title: Govern a shared schema across repos
description: Vendor one canonical JSON Schema into each consuming repository with docmeta schemas vendor, so CI validates against a committed, hash-pinned copy instead of a live URL, keep the plain URL form where its tradeoff is acceptable, and stop a contributed document choosing its own schema.
---

import { Steps, Tabs, TabItem, Aside, CardGrid, LinkCard } from '@astrojs/starlight/components';

When you run docmeta across dozens of repositories, you do not want a copy of
the schema in each one that nobody maintains. Copies drift: one repo tightens a
field, another never gets the update, and the standard you thought you were
enforcing fractures.

There are two ways to hold one canonical schema, and they fail differently.

| | **Vendored** (recommended) | **Referenced by URL** |
|---|---|---|
| What the repo contains | The schema file, committed, plus a hash pin | One line naming a URL |
| What CI depends on | Its own checkout | The schema host answering within 10 seconds, on every job |
| Taking an update | Re-run one command; review the diff | Automatic — including when you did not want it |
| An upstream change you did not expect | Shows up as a pull request | Shows up as a build that started failing |
| Setup per repo | One command | One line |

Vendoring is the default recommendation because it moves the schema into the
consuming repository's own history: reviewable in a pull request, diffable when
it changes, and immune to the host being down. Start there, and keep the URL
form for the cases described in [When the URL form is enough](#when-the-url-form-is-enough).

## Vendor the schema

<Steps>

1. **Publish the schema at a stable, versioned URL.** Put the version in the
   path so each release has its own immutable URL — for example
   `https://schemas.example.com/house/2.1.json`, then `.../house/2.2.json`. This
   is still worth doing when consumers vendor: the URL is what they vendor
   *from*, and what a re-vendor points at.

2. **In each consuming repo, run `schemas vendor`.**

   ```sh
   npx -y docmeta schemas vendor https://schemas.example.com/house/2.1.json
   ```

   docmeta downloads the schema, writes it to `./schema/2.1.json`, and records
   both where it came from and what it hashes to:

   ```
   Vendored https://schemas.example.com/house/2.1.json
     file       schema/2.1.json (266 bytes)
     integrity  sha256-c12b1cfe…7341
     config     docmeta.config.yaml (created)
   ```

   The config now points at the local copy:

   ```yaml title="docmeta.config.yaml"
   schemas:
     - ref: ./schema/2.1.json
       source: https://schemas.example.com/house/2.1.json
       integrity: sha256-c12b1cfe…7341
   ```

3. **Commit both.** The downloaded file and the config change belong in the same
   commit. This is the step the whole approach rests on — see the caution below.

4. **Validate as usual.** Nothing else changes:

   ```sh
   npx -y docmeta validate "docs/**/*.md"
   ```

   The schema host can now be down, moved, or retired, and this repo's gate keeps
   working. What it validates against is in the checkout.

5. **Take an update deliberately.** When the standard moves, re-run the command
   with the new URL:

   ```sh
   npx -y docmeta schemas vendor https://schemas.example.com/house/2.2.json
   ```

   The existing entry is replaced rather than duplicated, and the result is a
   pull request whose diff shows exactly what changed in the contract — the same
   ergonomics as a lockfile.

</Steps>

<Aside type="caution" title="A vendored schema git ignores is worse than no schema">
An ignored copy validates perfectly on the machine that downloaded it and is
simply *absent* in CI, where the failure arrives as a missing schema file in a
repository nobody changed. So `schemas vendor` asks `git check-ignore` about the
target **before** it downloads anything and refuses (exit 2) if the answer is
yes — which is also why the default is `./schema` and not `.docmeta/`, a
directory docmeta expects you to ignore wholesale.

Outside a repository, or with no `git` on `PATH`, the check cannot run. docmeta
says so on stderr and continues; make sure the file is tracked.
</Aside>

### Migrating a repo that already references the URL

If a repo already carries the URL form, vendoring converts it in place. Run the
command with the same URL it already references:

```sh
npx -y docmeta schemas vendor https://schemas.example.com/house/2.1.json
```

The bare-URL entry is **replaced**, not appended to, so the URL survives as
provenance (`source:`) and stops being a live dependency. The rest of the
config, comments included, is untouched.

### What the hash pin buys, and what it costs

`integrity` is recorded because vendoring means "I want these exact bytes". On
every run the file's bytes are hashed and compared before the schema is parsed.
A mismatch stops the run with exit 2 and no fallback:

```
docmeta: Schema "./schema/2.1.json" does not match its recorded integrity.
  expected sha256-c12b1cfe…7341
  found    sha256-9091a816…46cb
The file's contents have changed since it was vendored. Re-download it with
`docmeta schemas vendor https://schemas.example.com/house/2.1.json`, or update
the recorded integrity if the change was intended.
```

That is the cost, stated plainly: an edit to the vendored file that does not go
through `schemas vendor` — including a well-meant local tweak — breaks the build
until the pin is updated. In exchange, no copy of the shared standard can drift
without a reviewer seeing it. If you want the local file without the pin, delete
the `integrity:` line; `ref` and `source` keep working on their own.

<Aside type="tip" title="Keep the file byte-exact">
The one thing that moves the bytes without anyone editing them is a checkout
converting line endings. If your repository normalizes them, add a
`.gitattributes` rule:

```
schema/*.json -text
```

docmeta recognizes this case specifically and says so rather than reporting it
as changed contents.
</Aside>

## When the URL form is enough

A plain URL reference is one line and needs no command, and for some setups that
is the right trade:

- an **internal repo on the same infrastructure** as the schema host, where the
  host being down already means nobody is working;
- a **prototype or spike** where a broken build costs nothing;
- **checking a candidate schema** for one run, with `-s`:

  ```sh
  npx -y docmeta validate "docs/**/*.md" -s https://schemas.example.com/house/3.0.json
  ```

State the tradeoff rather than hiding it: with a URL reference, every job in
every consuming repo depends on that host answering within 10 seconds, and they
all fail at the same moment when it does not. A URL that is *mutable*
(`.../house/latest.json`) adds a second failure: the meaning of your build can
change overnight without a commit anywhere in your repository.

With vendoring, that same mutable-URL case degrades to "your committed copy is
stale" — visible, safe, and fixed by a re-vendor — instead of "your build
changed meaning while you slept."

### How a URL reference behaves

A URL reference can be supplied the same three ways any reference can.

<Tabs>
<TabItem label="In the file ($schema)">

A document names its own schema with a `$schema` key in its frontmatter.

```yaml title="docs/concepts/overview.md"
---
$schema: https://schemas.example.com/house/2.1.json
type: concept
---
```

</TabItem>
<TabItem label="In docmeta.config.yaml">

```yaml title="docmeta.config.yaml"
schemas:
  - https://schemas.example.com/house/2.1.json
```

This is the form `schemas vendor` replaces. You can also scope a URL schema to a
subtree with an `overrides` entry — see the [configuration
reference](/docmeta/reference/configuration/).

</TabItem>
<TabItem label="On the command line (--schema)">

```sh
npx -y docmeta validate "docs/**/*.md" -s https://schemas.example.com/house/2.1.json
```

`-s` overrides `$schema` and config for the whole run.

</TabItem>
</Tabs>

Whichever source supplies it, the schema set for each file is resolved by the
same precedence chain (`--schema` → file `$schema` → config `overrides` → config
`schemas` → built-in default). Vendoring does not change that chain; it changes
what one reference in it points at. For the full chain, see the [schema
resolution reference](/docmeta/reference/schema-resolution/).

Each fetch is bounded by a **10-second timeout**, retried **once** after roughly
500 ms on a network error or a `5xx` (never on a `4xx`, which will not heal),
and cached in memory for the rest of the run, so two thousand files sharing one
URL make one request. Successful fetches are also written to a [cross-run disk
cache](/docmeta/reference/schema-resolution/#the-cross-run-cache) — which speeds
up your local edit loop and does **not** help CI, because a hosted runner starts
with an empty workspace on every job.

### When a fetch fails

A URL schema that cannot be turned into a usable schema fails the *run*. docmeta
raises an operational error and exits `2`, distinct from a validation failure
(exit `1`), so a gate can tell "a document is non-conformant" from "the schema
host is unreachable". For the full contract, see [Exit codes & PR
annotations](/docmeta/ci/exit-codes-and-annotations/).

| Failure | What docmeta reports |
|---|---|
| The request exceeds the 10-second timeout | `Failed to fetch schema "<url>": timed out after 10000ms.` |
| The server responds with a non-2xx status | `Failed to fetch schema "<url>": HTTP <status>.` |
| The host is unreachable or the request errors | `Failed to fetch schema "<url>": <reason>.` |
| The response body is not valid JSON | `Schema "<url>" did not return valid JSON: <reason>.` |
| The body parses but is not a schema | `Schema "<url>" does not look like a JSON Schema: …` |

That last row matters more than it looks. An API gateway or a misconfigured
bucket commonly answers a bad path with `200 OK` and a JSON error envelope,
which would otherwise compile as a schema with no constraints and pass every
document — a green gate that has stopped working. docmeta [refuses
it](/docmeta/reference/schema-resolution/#what-docmeta-requires-of-a-fetched-schema),
on the vendoring path as well, so an envelope can never be committed as your
contract.

<Aside type="tip" title="Keep the schema's own dialect explicit">
docmeta auto-detects a schema's JSON Schema dialect from its own `$schema`
meta-schema URI (2020-12, 2019-09, draft-07, draft-06, and draft-04; a schema
with no `$schema` is treated as 2020-12). Set `$schema` explicitly in the
published schema so its dialect is unambiguous to every consumer.
</Aside>

## When your repo takes outside pull requests

Everything above governs where *your* canonical schema comes from. One more
thing decides whether a repository is actually judged by it.

A document's own `$schema` sits **above** config in the [precedence
chain](/docmeta/reference/schema-resolution/#precedence). That is the feature
that lets a page carry its own contract — and in a repo whose pull requests come
from people you have not met, it is also a way to opt out of yours. One line of
frontmatter, and that file is judged by a schema the contributor chose:

```yaml title="contributed.md"
---
title: Contributed page
$schema: https://example.invalid/permissive.json
---
```

Serve `{"type": "object"}` from that URL and the file passes everything. Worse,
the run reads as a *partial* success — the contributed file green, the honest
files still red against your real schema — so nothing about the output looks
like a bypass:

```
✓ contributed.md
✗ honest.md
    (root)  must have required property 'type'  (line 1)  [google:okf:0.1]
```

Note what this walks past: `schemas:`, the vendored copy, and the integrity pin
all sit *below* `$schema` in the chain, so none of the durability work above
applies to that file.

One key closes it:

```yaml title="docmeta.config.yaml"
schemas:
  - ref: ./schema/2.1.json
    source: https://schemas.example.com/house/2.1.json
    integrity: sha256-c12b1cfe…7341
schemaTrust:
  documentRefs: local
```

Now the contributed file fails with the reason on the file itself, and every
other document is validated exactly as before:

```
✗ contributed.md
    Refusing the "$schema" URL "https://example.invalid/permissive.json":
    schemaTrust.documentRefs is "local" …
```

It is a **failing file**, exit 1 — not a stopped run — so with `--format github`
the annotation appears on that line of the pull request, where the contributor
can act on it.

What `local` still allows is worth stating, because it is why turning it on is
cheap: a built-in id (`$schema: google:okf:0.1`) and a schema file committed in
the repository both keep working. Only a URL, and a path reaching outside the
repository, are refused. And `-s/--schema` is untouched in every mode — you can
still check a candidate schema for one run.

`documentRefs: none` goes one step further: the document's key is ignored
entirely and the config decides for every file, with one line on stderr naming
each file whose reference was dropped.

<Aside type="caution" title="Two things to know before you rely on it">
**An allowlist is not the strong setting.** `schemaTrust.hosts` narrows which
hosts a document-supplied URL may name, but `fetch` follows redirects, so an
allowlisted host answering `302` sends the request wherever it likes. Use
`hosts` for a known publisher; use `documentRefs: local` when you actually
distrust the contributor.

**Pin the version in CI.** A docmeta older than 3.11 does not know the key,
ignores it, and reports nothing — so the guard is only as real as the binary
your workflow runs:

```sh
npx -y docmeta@4 validate "docs/**/*.md"
```
</Aside>

## Verify it works

The `json` output reports the resolved schema set per file, so a normal run on a
known-good file shows which reference a repo is actually wired to:

```sh
npx -y docmeta validate docs/concepts/overview.md --format json
```

In the JSON, the file's `schemas` array names either your vendored path or your
URL. A clean run exits `0`.

The check worth doing once per repo is the one that proves vendoring took: with
the schema file committed, temporarily block the schema host (or just note that
nothing in the run touches it) and confirm the gate still passes.
