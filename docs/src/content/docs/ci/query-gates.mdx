---

Schema validation judges one file at a time, and some of your rules don't live
in one file. A page that credits an author nobody has, two pages claiming the
same slug, a tag that appears exactly once — each document involved is
individually valid, so `validate` waves them all through. Catching them takes a
**join**, and that is what `docmeta query` is for: every file's metadata
becomes one row in a SQL table, and any query that returns rows can fail the
build.

Nothing new is installed for this. The engine is `node:sqlite`, which ships in
the Node.js your runner already has.

## One file, one row

`query` builds an in-memory table named `docs` from the files you point it at:
one row per file, one column per top-level metadata key, plus four system
columns — `_path` (the file), `_format`, `_present` (did the file carry
metadata at all), and `_data` (the whole block as JSON, for reaching into
nested values with `->>` and `json_each`). The [CLI
reference](/docmeta/reference/cli/#query) has the full contract.

Retrieval is plain SQL. A tag census over a corpus:

```bash
npx docmeta query "SELECT t.value tag, count(*) n
  FROM docs, json_each(docs.tags) t
  GROUP BY tag ORDER BY n DESC, tag" docs/
```

```
tag    n
guide  2
api    1
intro  1
3 rows
```

## Turn a join into a gate

`--check` makes rows mean findings: any result row exits `1`, an empty result
exits `0`. That is the whole contract — the query itself is the rule, so
anything you can phrase as "SELECT the violations" is now a CI gate.

The dangling-reference classic — docs credit authors by slug, and one cited
author has no page:

```bash
npx docmeta query --check "SELECT d._path, d.author
  FROM docs d
  LEFT JOIN docs a ON a.slug = d.author AND a._path LIKE '%authors%'
  WHERE d._path LIKE '%docs%' AND d.author IS NOT NULL
    AND a._path IS NULL" docs/ authors/
```

```
_path          author
docs/gamma.md  ghost
✗ 1 row — check failed
```

Duplicate slugs, same shape:

```bash
npx docmeta query --check "SELECT slug, count(*) n
  FROM docs GROUP BY slug HAVING n > 1" docs/
```

In CI it is one more step beside the `validate` gate, and the exit codes mean
the same things they mean everywhere in docmeta — `0` clean, `1` findings, `2`
operational error ([the contract](/docmeta/reference/output-and-exit-codes/)):

```yaml title=".github/workflows/docs.yml"
- name: Cross-file metadata rules
  run: |
    npx -y docmeta query --check \
      "SELECT slug, count(*) n FROM docs GROUP BY slug HAVING n > 1" \
      "docs/**/*.md"
```

<Aside type="tip" title="Where do the queries live?">
A gate is a rule your team agreed on, so keep the SQL where rules live: in the
workflow file, or in a small script the workflow calls. Each query gets a name
(`dangling-authors`, `duplicate-slugs`), each name is one CI step, and a red
check tells the contributor which rule they broke.
</Aside>

## Feed the same table to your tooling

`--format json` prints the bare result array — rows for a read, change objects
for an edit — for the same subprocess-and-parse pipelines that consume
[validation results](/docmeta/ci/consume-results/):

```bash
npx docmeta query "SELECT _path, title FROM docs WHERE draft = 1" docs/ -f json
```

`--db <path>` also writes the built table to a SQLite file, so anything that
speaks SQLite can browse it — `sqlite3`, Datasette, DuckDB:

```bash
npx docmeta query --db docs.db docs/    # export only; SQL is optional
```

The export is a regenerated artifact of your corpus: rebuild it whenever you
like, and don't edit it expecting the files to notice. If you work from a
checkout of the docmeta repo itself, `node scripts/query-ui.mjs` serves that
export into Datasette Lite in your browser, write panel included — it is repo
tooling, not part of the published package.

## Writes exist, and preview is the default

The same table accepts standard DML — `UPDATE` sets keys (`SET k = NULL`
removes them), `INSERT` creates files, `DELETE` strips a metadata block, and
`ALTER TABLE` evolves the governing schema itself. Every mutating statement is
a **preview** until you pass `--write`; the preview is the exact diff, and
`--check` counts pending changes as findings, which turns any backfill into a
drift gate:

```bash
npx docmeta query "UPDATE docs SET reviewed = 'todo'
  WHERE reviewed IS NULL AND _present = 1" docs/
```

```
docs/alpha.md: reviewed: (unset) -> todo
docs/beta.md:  reviewed: (unset) -> todo
docs/gamma.md: reviewed: (unset) -> todo
3 changes across 3 files — dry run; pass --write to apply
```

Statements that could write outside the corpus refuse by name — `ATTACH`,
`VACUUM`, `DROP TABLE`, multi-statement input — and the refusal says what to
run instead. The [vocabulary table](/docmeta/reference/cli/#query) is the
complete list of what each statement means in file terms; the schema-editing
half of it (`ALTER`) is the one-statement ratchet covered in the journeys
below.
