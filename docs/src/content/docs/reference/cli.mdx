docmeta exposes four subcommands: [`validate`](#validate) (the default),
[`get`](#get), [`fill`](#fill), and [`schemas`](#schemas), the last of which is a
group with its own [`infer`](#schemas-infer) and [`vendor`](#schemas-vendor)
subcommands. `validate`, `get`, `fill`, and `schemas infer` — every command that
takes paths — share an [input model](#shared-input-model) and several flags with
identical semantics.

```sh
docmeta [global options] [command] [command options] [arguments]
```

## Global options

Global options are accepted before the subcommand.

| Option | Description |
|---|---|
| `-V, --version` | Print the docmeta version and exit. |
| `--no-color` | Disable colored output. See [color behavior](/docmeta/reference/output-and-exit-codes/#color-behavior). |
| `-h, --help` | Print help for the program or a subcommand. |

`validate` is the default command, so `docmeta <paths...>` runs validation
without naming the subcommand.

## `validate`

Validate the metadata in the given files, directories, or globs against the
resolved [schema set](/docmeta/reference/schema-resolution/) for each file. This is the
default command.

```sh
docmeta validate [paths...] [options]
docmeta [paths...] [options]
```

### Arguments

| Argument | Description |
|---|---|
| `[paths...]` | Files, directories, or globs to validate. Use `-` to read from stdin. Optional — falls back to config `paths:`. See the [shared input model](#shared-input-model). |

### Options

| Option | Argument | Default | Description |
|---|---|---|---|
| `-s, --schema` | `<ref>` | — | Schema to validate against. Repeatable. When given, it overrides `$schema` and config for every file. See [reference kinds](/docmeta/reference/schema-resolution/#reference-kinds). |
| `--ext` | `<list>` | supported extensions | Comma-separated extensions used when expanding directories and globs. |
| `--exclude` | `<glob>` | — | Glob to exclude from directory and glob walks. Repeatable. Merged with config `exclude:` and the [default ignores](#default-ignores). |
| `--as` | `<format>` | — | Force an input [format](/docmeta/reference/formats/) (extractor name, e.g. `markdown`). Required when reading from stdin. |
| `-f, --format` | `<pretty\|json\|github\|sarif\|junit>` | `pretty` | [Output format](/docmeta/reference/output-and-exit-codes/). An unknown value is an error (exit 2). |
| `-c, --config` | `<path>` | discovered | Path to a [config file](/docmeta/reference/configuration/). When set, the file must exist or docmeta exits 2. |
| `--no-config` | — | off | Ignore any discovered config file and run on the [built-in default schema set](/docmeta/reference/schema-resolution/#precedence). `-c` and `--no-config` set the same option, so the one written later on the command line wins. |
| `-q, --quiet` | — | off | In `pretty` output, hide passing files. Has no effect on `json`, `github`, `sarif`, or `junit`. |
| `--allow-empty` | — | off | Treat zero matched files as success instead of an error (exit 2). See [empty input sets](#empty-input-sets). |
| `--no-gitignore` | — | on | Validate files `.gitignore` covers as well. Filtering is on by default; see [default ignores](#default-ignores). Overrides config `respectGitignore:`. |
| `--offline` | — | off | Never fetch a remote schema. A `url` reference is served from the [schema cache](/docmeta/reference/schema-resolution/#the-cross-run-cache); one that is not cached is an error (exit 2) naming the URL. Built-in and local-file references are unaffected. Overrides config `offline:`. |
| `--baseline` | `[path]` | config `baseline:`, else `.docmeta-baseline.json` | Compare findings against a recorded [baseline](#baselines) and fail only on new ones. The value is optional, and omitting it means *this project's* baseline: the configured `baseline:` path when there is one, resolved against the config file, otherwise `.docmeta-baseline.json`. Config `baseline:` turns this on for every run. A named file that does not exist is an error (exit 2). |
| `--write-baseline` | `[path]` | config `baseline:`, else `.docmeta-baseline.json` | Record this run's findings as the baseline, then exit 0. The value is optional. Wins over `--baseline`. Findings from `-` (stdin) are the one exception: they cannot be recorded, so they still fail the run. |
| `--no-baseline` | — | off | Ignore a baseline supplied by config `baseline:` for this run. `--baseline` and `--no-baseline` set the same option, so the one written later on the command line wins. |

<Aside type="note">
Repeatable flags (`-s/--schema`, `--exclude`) accumulate; pass the flag once per
value, for example `-s a -s b`.
</Aside>

### Baselines

A baseline records the violations that exist today so that a run fails only on
findings that are **new**. That is what lets a field become `required`
immediately on a repo with a large backlog, instead of after a cleanup: the rule
applies to everything written from now on, and the debt stays visible rather
than blocking the build.

```sh
docmeta validate --write-baseline   # record today's findings, then exit 0
docmeta validate --baseline         # from now on, fail only on new ones
```

The file is JSON, path-keyed, with a sorted array of violation fingerprints per
document, so it diffs and merges legibly:

```json title=".docmeta-baseline.json"
{
  "version": 1,
  "generatedWith": "3.4.2",
  "entries": {
    "docs/api/legacy.md": ["a1b2c3d4e5f60718", "9f8e7d6c5b4a3210"],
    "docs/guides/old.md": ["1122334455667788"]
  }
}
```

Commit it. Reviewers should see it grow or shrink in a diff.

A fingerprint is 16 hex characters of
`sha256(schema + NUL + instancePath + NUL + keyword + NUL + subject)` — the four
[machine-stable fields](/docmeta/reference/output-and-exit-codes/#json) of a
violation. It deliberately excludes the **line number**, so editing a document
does not invalidate it; the **message prose**, so an Ajv upgrade that rewords a
message does not invalidate every entry at once; and the **file path**, which is
already the key.

Three things do change a fingerprint, and each is recovered with one
`--write-baseline`:

- **Renaming a document.** Entries are path-keyed, so a rename moves findings to
  a key with no entry and every one of them reads as new. The
  `N no longer occur` line in the summary is the hint that a rename, not a
  regression, is what happened.
- **Re-pointing a schema.** The schema reference is part of the identity, so
  switching `google:okf:0.1` to a URL serving the same schema changes every
  fingerprint. docmeta cannot tell it is the same contract.
- **Editing a `pattern`, `enum`, or `minLength` rule.** Those keywords have no
  stable `subject`, so a violation of the edited rule keeps its fingerprint —
  but a violation that moves to a *different* keyword does not.

A local file schema reference is measured **relative to the config file's
directory**, and so is a `baseline:` path, so the same repo produces the same
fingerprints whether the command runs from the repo root or from a
subdirectory.

Findings the baseline already holds do not fail the run and are reported
instead:

```
✓ docs/api/legacy.md  (2 baselined)

1 file checked, 1 passed, 0 failed, 0 errors
3 baselined findings, 1 no longer occurs — run --write-baseline to prune
```

Entries that no longer occur are **never fatal** — they are only reported, so a
run that fixes violations stays green. `--write-baseline` reports its change in
both directions:

```
Baseline written to .docmeta-baseline.json
  14 findings recorded (+2 new, -12 no longer occur)
```

<Aside type="caution">
`--write-baseline` replaces the file with what *this run* saw, so a narrowed
glob or a mistyped `--exclude` forgives every finding it did not reach. The
`-12 no longer occur` count is the only thing that makes that visible; a
re-record reporting a drop you cannot explain should not be committed.
</Aside>

### Examples

```sh
docmeta validate docs/                          # walk a directory
docmeta validate "**/*.md" -f github            # CI annotations
docmeta validate "**/*.md" -f sarif > out.sarif # code scanning
docmeta validate "**/*.md" -f junit > junit.xml # the CI "Tests" tab
docmeta validate page.md -s google:okf:0.1 -s ./my.schema.json
cat page.md | docmeta validate - --as markdown  # read from stdin
docmeta validate --write-baseline               # record today's backlog
docmeta validate --baseline                     # fail only on new findings
```

## `get`

Print the values of one or more metadata fields from each file. Useful for
scripted extraction. `get` reads and reports values; it does not validate.

```sh
docmeta get --fields <list> [paths...] [options]
docmeta get [fields] [paths...] [options]
```

### Arguments

| Argument | Description |
|---|---|
| `[fields]` | Comma-separated metadata field references to print, when `--fields` is not used. Each is a top-level key (`title`), a dot-notation path into nested objects and arrays (`author.name`, `tags.0`), or a [JSON Pointer](https://datatracker.ietf.org/doc/html/rfc6901) when prefixed with `/` (`/author/name`, `/tags/0`). See [naming the fields](#naming-the-fields). |
| `[paths...]` | Files, directories, or globs to read. Use `-` to read from stdin. Optional — falls back to config `paths:`. See the [shared input model](#shared-input-model). |

A requested field that is absent from a file is reported as unset rather than
as an error.

#### Naming the fields

The field list can be given either way, and there is one rule:

> If `--fields` is present, **every** positional is a path. Otherwise the first
> positional is the field list.

```sh
docmeta get title,type docs/intro.md          # positional field list
docmeta get --fields title,type docs/intro.md # the flag; both positionals are paths
docmeta get --fields title                    # no paths: config `paths:` applies
```

`--fields` is the same flag [`fill`](#fill) takes, and it is the unambiguous
spelling: with it, nothing about a path can be mistaken for a field.

Naming no fields at all is an error (exit 2) rather than an empty report. So is
a *path* in the field-list position, which is the mistake the positional form
invites:

```console
$ docmeta get docs/intro.md
docmeta: "docs/intro.md" looks like a path, not a field list. Pass fields first
(docmeta get title docs/intro.md) or use --fields.
exit=2
```

A token is read as a path when it exists on disk, is a glob, ends in a
[supported extension](/docmeta/reference/formats/), or contains a path
separator. A comma-separated list and a leading-slash JSON Pointer are
recognized as fields, so a normal field list is not mistaken for a path — but
"exists on disk" is checked first, so a pointer that happens to match a real
absolute file is read as a path. `--fields` is the unambiguous spelling
whenever the guess would be wrong.

#### Nested fields

A field reference descends into nested objects and arrays. Two syntaxes are
accepted:

- **Dot-notation**: `author.name`, `tags.0`. Concise, but a key containing a
  literal `.` cannot be addressed this way.
- **JSON Pointer** ([RFC 6901](https://datatracker.ietf.org/doc/html/rfc6901)):
  any reference beginning with `/`, e.g. `/author/name` or `/tags/0`. This is
  the same pointer `validate` prints in error locations, so a path copied from a
  validation failure works verbatim. Use it to address keys that contain dots
  (`/odd.key`) or slashes (`/a~1b` for the key `a/b`).

Requesting a parent key (`author`) returns the whole nested value. A path that
descends into a scalar, or whose segment is missing, is reported as unset. Only
a key's own properties resolve; inherited members such as `toString` or
`__proto__` are treated as missing.

On Git Bash/MSYS2 (Windows), quote a leading-slash pointer, `'/author/name'`,
so the shell does not rewrite it as a filesystem path. Other shells are
unaffected.

### Options

| Option | Argument | Default | Description |
|---|---|---|---|
| `--fields` | `<list>` | the `[fields]` positional | Comma-separated fields to print. When given, **every** positional is a path. See [naming the fields](#naming-the-fields). |
| `--ext` | `<list>` | supported extensions | Comma-separated extensions used when expanding directories and globs. |
| `--exclude` | `<glob>` | — | Glob to exclude from directory and glob walks. Repeatable. Merged with config `exclude:` and the [default ignores](#default-ignores). |
| `--as` | `<format>` | — | Force an input [format](/docmeta/reference/formats/) (extractor name). Required when reading from stdin. |
| `-f, --format` | `<pretty\|json>` | `pretty` | Output format. `sarif` and `junit` are `validate`-only, and `github` is available on `validate` and [`fill`](#fill). An unknown value is an error (exit 2). |
| `-c, --config` | `<path>` | discovered | Path to a [config file](/docmeta/reference/configuration/). When set, the file must exist or docmeta exits 2. |
| `--no-config` | — | off | Ignore any discovered config file and run on the [built-in default schema set](/docmeta/reference/schema-resolution/#precedence). `-c` and `--no-config` set the same option, so the one written later on the command line wins. |
| `-q, --quiet` | — | off | In `pretty` output, hide files where **every** requested field is unset. A file with any value present still prints, `(unset)` included — quiet hides files, never values. Has no effect on `json`. |
| `--allow-empty` | — | off | Treat zero matched files as success instead of an error (exit 2). See [empty input sets](#empty-input-sets). |
| `--no-gitignore` | — | on | Read files `.gitignore` covers as well. Filtering is on by default; see [default ignores](#default-ignores). Overrides config `respectGitignore:`. |
| `--offline` | — | off | Accepted for parity with `validate` and `fill`. It has no effect here: `get` prints extracted values and never loads a schema, so it makes no network requests to suppress. |

### Output

In `pretty` format, `get` prints one `<file>: <field>=<value>` line per
requested field per file. Unset fields print as `(unset)`. In `json` format it
prints an array of `{ file, present, values }` objects, where `values` maps each
requested field to its value; a requested field that is unset is omitted from
`values`. `present` reports whether the file had a metadata block at all.

### Examples

```sh
docmeta get title,type docs/intro.md
docmeta get --fields title,type docs/intro.md
docmeta get author.name,/author/email docs/intro.md
docmeta get type "**/*.md" -f json
docmeta get owner "docs/**/*.md" -q          # only the files that set it
cat page.md | docmeta get title - --as markdown
```

## `query`

Run one SQL statement over the metadata of every input file at once. Where
[`get`](#get) answers per file, `query` answers across the corpus — filters,
aggregation, and joins, including the cross-file rules no single-document
schema can express: every `author:` names an author page that exists, no two
pages share a `slug:`, nothing published is stale. With `--check`, returned
rows are findings and the exit code says so, which makes any such rule a CI
gate.

```sh
docmeta query --query <sql> [paths...] [options]
docmeta query [sql] [paths...] [options]
```

### Arguments

| Argument | Description |
|---|---|
| `[sql]` | One SQL statement, run against the `docs` table described below, when `--query` is not used. A second statement after a `;` is refused rather than silently ignored. Optional when `--db` is given — exporting needs no query. |
| `[paths...]` | Files, directories, or globs to load. Use `-` to read from stdin. Optional — falls back to config `paths:`. See the [shared input model](#shared-input-model). |

The same rule as `get`'s field list applies: if `--query` is present, **every**
positional is a path; otherwise the first positional is the SQL. A token in the
SQL slot that looks like a path is an error naming the remedy, and `-` is
always stdin, never SQL.

### The `docs` table

One row per input file. Your top-level metadata keys become columns, holding
the values the files had: strings and numbers as themselves, booleans as
`1`/`0`, arrays and objects as JSON text — which SQLite's
[`json_each`](https://sqlite.org/json1.html) and `->>` query directly. A key
that is absent from a file is SQL `NULL` in that row. Unusual key names are
ordinary quoted identifiers: `SELECT "sidebar position" FROM docs`.

Four columns are docmeta's own, prefixed so frontmatter cannot collide with
them (a frontmatter key with exactly one of these names is not lifted to a
column and stays reachable through `_data`):

| Column | Value |
|---|---|
| `_path` | The file's path as docmeta prints it everywhere: relative, `/`-separated on every platform, sorted. `<stdin>` for piped input. |
| `_format` | Extractor name (`markdown`, `html`, `xml`, …). |
| `_present` | `1` if the file has a metadata block/surface, else `0` — so `WHERE _present = 0` lists files with no metadata at all. |
| `_data` | The complete extracted metadata as JSON text, for `json_extract`/`->>` reach into nested values and unlifted keys. |

The database is built in memory on every run and discarded (`--db` exports a
copy; `--write` applies a statement's changes to the files — see below).
Statements are judged by their **effects** on this disposable projection:
reads return rows; metadata-column changes become a per-file diff; an added
row is a file created, a removed row a front matter block stripped, and a
`_path` move a file rename. Files are never *deleted* through SQL, and the
other system columns are read-only. Like `get`, `query` resolves no schema
and makes no network requests.

### Options

| Option | Argument | Default | Description |
|---|---|---|---|
| `--query` | `<sql>` | the `[sql]` positional | The SQL statement. When given, **every** positional is a path. |
| `--check` | — | off | Treat returned rows as findings: exit 1 if the query returns any, 0 if it returns none. The `pretty` verdict line shows ✓/✗. |
| `--db` | `<path>` | — | Also write the built database to this file; the SQL is then optional. The file is a regenerated artifact: an existing SQLite database at the path is overwritten, anything else is refused. See [exporting the database](#exporting-the-database). |
| `--write` | — | off | Apply a mutating statement's changes to the files. Without it, the same statement is a **preview**: the per-file diff it would make, nothing touched. See [writing back](#writing-back). |
| `--ext` | `<list>` | supported extensions | Comma-separated extensions used when expanding directories and globs. |
| `--exclude` | `<glob>` | — | Glob to exclude from directory and glob walks. Repeatable. Merged with config `exclude:` and the [default ignores](#default-ignores). |
| `--as` | `<format>` | — | Force an input [format](/docmeta/reference/formats/) (extractor name). Required when reading from stdin. |
| `-f, --format` | `<pretty\|json>` | `pretty` | Output format. An unknown value is an error (exit 2). |
| `-c, --config` | `<path>` | discovered | Path to a [config file](/docmeta/reference/configuration/). When set, the file must exist or docmeta exits 2. |
| `--no-config` | — | off | Ignore any discovered config file. `-c` and `--no-config` set the same option, so the one written later on the command line wins. |
| `--allow-empty` | — | off | Treat zero matched files as success instead of an error (exit 2). See [empty input sets](#empty-input-sets). |
| `--no-gitignore` | — | on | Load files `.gitignore` covers as well. Filtering is on by default; see [default ignores](#default-ignores). Overrides config `respectGitignore:`. |
| `--offline` | — | off | Accepted for parity with the other commands. It has no effect here: `query` never loads a schema, so it makes no network requests to suppress. |

There is no `-q/--quiet`: `get` uses it to hide files and `validate` to hide
passes, and a query result has no analogous noise — the rows are exactly what
was asked for.

### Exporting the database

`--db <path>` writes the same table to a SQLite file for any other tool to
open. With no SQL, the export is the whole job:

```sh
docmeta query --db docs.db docs/
datasette docs.db        # a browsable UI and JSON API over the corpus
```

[Datasette](https://datasette.io/) is the natural front-end, and its
[Datasette Lite](https://lite.datasette.io/) build runs entirely in the
browser — serve the file over local HTTP with CORS and nothing but Node is
required. This repository's `npm run query:ui` does exactly that for its own
docs. The export is plain SQLite: `sqlite3`, DuckDB, Grafana, or anything
else that reads the format works the same way.

### Writing back

An `UPDATE` against `docs` edits the corpus — through the same
comment-preserving, self-verifying writer `fill` uses, never through text
substitution:

```sh
# Preview: the per-file diff, nothing touched
docmeta query "UPDATE docs SET draft = false WHERE draft IS NULL" docs/
# Apply it
docmeta query --write "UPDATE docs SET draft = false WHERE draft IS NULL" docs/
# Hold it in CI: pending changes fail until someone runs --write
docmeta query --check "UPDATE docs SET draft = false WHERE draft IS NULL" docs/
```

Preview is the default on purpose — one statement can touch every file, and
the human reading the diff is the gate (`fill` writes by default because each
of its values passed a confidence gate first). Values are restored to the
types the files had: `1`/`0` back to booleans, JSON text back to arrays and
objects, with the column's dominant type deciding for a key the file never
had. A value the restored type cannot hold, invalid JSON, a read-only
target, a bad or colliding path, or a file that changed on disk since it was
read — each refuses the **whole run** by file and key before anything is
written. `ATTACH` and `VACUUM` are refused by name (they can write files of
their own, outside the effect gate), and `DROP TABLE` is refused as the
accident-shaped spelling of two real statements.

The vocabulary is standard SQL (proposal 0024):

| Statement | Meaning |
|---|---|
| `UPDATE docs SET k = v` | set a key; a corpus-new key widens the table |
| `UPDATE docs SET k = NULL` | **remove** the key from matching files (absent = no-op) |
| `UPDATE docs SET k = explicit_null()` | write a literal `k: null` — the rare case |
| `UPDATE docs SET _path = '…'` | move/rename the file, body byte-preserved; same extension only |
| `INSERT INTO docs (_path, …) VALUES (…)` | create a file: that front matter, an empty body |
| `DELETE FROM docs WHERE …` | strip the front matter block; the file and its body survive |
| `ALTER TABLE docs ADD COLUMN k TYPE [NOT NULL] [DEFAULT v]` | **DDL**: the resolved schema gains property `k` (required if NOT NULL); a DEFAULT backfills every file |
| `ALTER TABLE docs DROP COLUMN k` | **DDL**: the schema loses `k`, and the key is removed from every file |
| `ALTER TABLE docs RENAME COLUMN a TO b` | **DDL**: the schema property is renamed, and the key renamed in every file, values carried verbatim |

Key deletion and block-stripping work wherever the metadata lives in fenced
front matter (markdown, MDX, AsciiDoc, reStructuredText); element-backed
keys in HTML/XML refuse rather than half-delete, and `INSERT` creates only
formats whose writer can build a block (markdown, MDX).

**DDL edits the schema itself.** An `ALTER` statement resolves the run's
schema set (which must be a single set — a corpus split by overrides refuses;
scope the run to one group) with the same trust boundary as `validate`: a
document's `$schema` cannot point the edit outside the repository. It then
evolves the one schema that owns the key: a **hand-maintained local schema
file is edited in place** — `properties` and `required` only, your indent,
git as the review surface, and a vendored file's `integrity:` pin refreshed
in the same write — while an **immutable built-in forks** to a local copy
(`schemas/<name>-<ver>.local.json` beside the config, `$id` suffixed
`+local`) with the config entry (either spelling, comments intact) and any
in-file `$schema` (string or list) repointed in the same write. Every file
the statement will touch appears in the preview, the config included. When
ownership is unclear, DDL refuses rather than guesses: a key another schema
in the set also declares or requires, an `ADD` onto an already-declared
property (its constraints would be lost), a `DEFAULT` the declared type
cannot hold, or a set naming several local schema files. URL refs refuse
with "vendor it first" (`docmeta schemas vendor`). A corpus resolving to the
built-in default set refuses too: there is no schema of yours to evolve, and
the `UPDATE` spellings cover every data-only case. The ratchet, whole:

```sh
docmeta query --write "ALTER TABLE docs
  ADD COLUMN reviewed TEXT NOT NULL DEFAULT 'pending'" docs/
# schema now requires `reviewed`, every file carries it, validate stays green
```

### Output and exit codes

In `pretty` format: an aligned table (header row, then values; SQL `NULL`
prints as `(null)`) followed by a row count — or, with `--check`, a ✓/✗ verdict
line. A mutating statement renders as its diff instead:
`<file>: <key>: <from> -> <to>` per change, then the mode's verdict (applied,
dry-run hint, or the `--check` ✓/✗). In `json` format: the bare array —
row objects for a read, `{ file, key, from, to, written }` change objects for
an edit; the `--check` verdict travels in the exit code, not the envelope.

With `--db` and no SQL, the export summary (`Wrote <path> …`) is the report;
with both, the rows own stdout and the export note goes to stderr as a
diagnostic.

Exit `0` — the query ran (with `--check`: and returned no rows or pending
changes; with `--write`: and applied cleanly). Exit `1` — only from `--check`
without `--write`, when rows or pending changes came back. Exit `2` —
operational, including SQL that cannot be prepared and every write refusal:
a broken or refused statement is a usage error, not a finding.

### Examples

```sh
docmeta query "SELECT _path, title FROM docs WHERE draft = 1" docs/
docmeta query "SELECT t.value tag, count(*) n FROM docs, json_each(docs.tags) t GROUP BY tag ORDER BY n DESC" docs/
docmeta query --check "SELECT slug, count(*) n FROM docs WHERE slug IS NOT NULL GROUP BY slug HAVING n > 1" docs/
docmeta query --check "SELECT d._path, d.author FROM docs d LEFT JOIN docs a ON a._path GLOB 'authors/*' AND a.slug = d.author WHERE d.author IS NOT NULL AND a._path IS NULL" docs/ authors/
docmeta query "SELECT _path FROM docs WHERE _present = 0" docs/   # nothing to validate yet
cat page.md | docmeta query "SELECT title FROM docs" - --as markdown
```

## `fill`

Infer values for the metadata properties that are missing or invalid, and write
back the ones the model is confident about. `fill` resolves the same
[schema set](/docmeta/reference/schema-resolution/) as `validate`, so the schema
you already maintain is what determines which properties get proposed.

```sh
docmeta fill [paths...] [options]
```

<Aside type="caution">
`fill` **writes to your files by default**. Pass `--dry-run` to preview
proposals without touching anything, and run it on a clean working tree so the
changes are easy to review.
</Aside>

`fill` sends the page and its schema to an LLM provider. By default it **detects
one**, taking the first of these that your machine can actually use:

1. `anthropic` — `ANTHROPIC_API_KEY` is set
2. `openai` — `OPENAI_API_KEY` is set
3. `claude-cli` — a `claude` CLI on your `PATH` that runs (`claude --version` succeeds; sign-in is not checked, so an unauthenticated CLI is still selected and fails at the first call)
4. `llama-cpp` — a local model, needing no key and costing nothing

Pass `--provider` to pin one instead. `fill` reports which provider and model it
used, in both output formats.

<Aside type="caution" title="The local fallback downloads">
  If detection gets all the way to `llama-cpp`, the first run fetches model
  weights — under 10 GB, sized to your machine — and, if the `node-llama-cpp`
  binding is missing, installs that too (roughly 700 MB). Both warn once before
  starting, and both go into `~/.hawkeyexl-inference/`, never your project.

  Set `INFERENCE_NO_AUTO_INSTALL=1` to refuse the binding install, or pass an
  explicit `--provider` to avoid the local model entirely. In CI, pin
  `--provider` (or set a key) so a build agent never pays for this.
</Aside>

### Which properties get filled

A schema property is a candidate when it is **missing** from the file's
metadata, or **present but invalid**. A property that is already present and
valid is never touched, and neither is `$schema`, which is schema wiring, not
metadata.

### The confidence gate

Every proposal carries a self-reported confidence between 0 and 1. That number is
a weak signal on its own, so it is the **last** of four gates. Three mechanical
checks run first, and a high confidence cannot override any of them:

1. **The value must satisfy the property's own subschema.** `fill` builds the
   response schema out of your schema's property definitions, so a `timestamp`
   that is not a valid `date-time` is rejected before it is ever scored. When
   several schemas in the set define the same property, every one of their rules
   applies, so `-s` order does not change what the model may propose.
2. **The property must be one docmeta asked about.** The model cannot introduce
   keys your schema does not define.
3. **The document must still validate afterwards.** Any value that would leave
   the page failing its own schema is reverted and reported.

Only then is `--confidence` applied. Values below the threshold are **skipped,
and reported by name and score** so you know what still needs a human. The
confidence and the model's reasoning stay in the report; they never reach your
document.

Because the cache stores the proposal *before* gating, re-running with a
different `--confidence` re-scores the cached proposals and costs nothing. That
is the intended way to tune the threshold on a real docset.

The cache lives in `.docmeta/cache` relative to the working directory. It is
machine-local and safe to delete at any time. Add `.docmeta/` to your
`.gitignore`. Pass `--no-cache` to bypass it entirely.

### Which formats can be written

`fill` can only write formats it can round-trip without disturbing the rest of
the document. `markdown` and `mdx` are always writable. `rst` and `asciidoc` are
writable **only when the file already has a fenced front matter block**, because their
native docinfo and header syntax is lossy to read back, and a bare `---` means
something else in both languages. `xml` (including `.dita` and `.ditamap`) and
`html` are writable. Run `docmeta schemas` to see the current writability of each
format. A file docmeta cannot write is reported as a per-file error, not a failed
run.

### Exit codes

`fill` exits **1** when a property your schema lists as `required` could not be
filled confidently, or when any file errored, which is work still to do. Skipped
*optional* properties are a normal outcome and leave the exit code at **0**. Usage
and operational failures exit **2**, as elsewhere.

### github annotations

`-f github` reports the work `fill` could **not** do: one
[workflow command](/docmeta/ci/exit-codes-and-annotations/#github) per property
the schema requires that was not filled — exactly the set that drives exit 1.
Optional skips stay silent, matching the exit-code rule.

```text
::error file=docs/api/legacy.md::[fill] /description is required and was not filled (confidence 0.42 is below the 0.7 threshold)
```

There is no `line=`. A proposal is about a property that is *missing* from the
document, so there is nothing in the file to point at; GitHub anchors a
file-only annotation to line 1.

<Aside type="caution" title="Not with stdin">
`docmeta fill - -f github` is a usage error (exit 2). With `-`, the filled
document owns stdout and the report goes to stderr — where GitHub never reads
`::error`. Annotations nobody can see would make a failing run look clean, so
the combination is refused rather than silently degraded.
</Aside>

The format is available whether or not `--dry-run` is set: annotations describe
what is still missing, which is as useful on a run that writes as on one that
previews.

### Examples

```sh
docmeta fill docs/ --dry-run                 # preview, write nothing
docmeta fill docs/ --confidence 0.9          # only near-certain values
docmeta fill page.md --fields description,tags
docmeta fill docs/ -f github                 # annotate what it could not fill
docmeta fill docs/ --dry-run -q              # only files with something to show
cat page.md | docmeta fill - --as markdown   # filled document to stdout
```

## `schemas`

List the built-in schemas and the supported input formats. On its own it takes
no positional arguments and reads no files. Its [`infer`](#schemas-infer)
subcommand reads your documents; its [`vendor`](#schemas-vendor) subcommand is
the one that reaches the network and writes to the repository.

```sh
docmeta schemas [options]
```

### Options

| Option | Argument | Default | Description |
|---|---|---|---|
| `-f, --format` | `<pretty\|json>` | `pretty` | Output format. Anything else is a usage error (exit `2`), including `github`, `sarif`, and `junit` — see [which command produces which format](/docmeta/ci/exit-codes-and-annotations/#output-formats). |

In `pretty` format, `schemas` lists each built-in schema by id and title, then
each input format with its extensions, whether it is implemented, and whether
[`fill`](#fill) can write to it. In `json` format it prints
`{ builtins, formats }`, where `builtins` is an array of
`{ id, title, description }` and `formats` is an array of
`{ name, extensions, implemented, writable }`.

```sh
docmeta schemas
docmeta schemas -f json
```

## `schemas infer`

Report what metadata your documents already carry, and draft a schema from it.
Purely statistical and **offline**: no inference provider, no network, no model.
It reads the metadata blocks, counts them, and prints a table.

```sh
docmeta schemas infer [paths...] [options]
```

### Arguments

| Argument | Description |
|---|---|
| `[paths...]` | Files, directories, or globs to scan. Use `-` to read from stdin. Optional — falls back to config `paths:`. See the [shared input model](#shared-input-model). |

### Options

| Option | Argument | Default | Description |
|---|---|---|---|
| `--out` | `<path>` | — | Write the draft schema to this file. Refuses to overwrite an existing file, and refuses a path `.gitignore` covers — see below. |
| `--min-coverage` | `<pct>` | `0` | Hide keys below this coverage percentage. The default shows everything, deliberately: the long tail is where "one team's convention" hides. |
| `--ext` | `<list>` | supported extensions | Comma-separated extensions used when expanding directories and globs. |
| `--exclude` | `<glob>` | — | Glob to exclude from directory and glob walks. Repeatable. Merged with config `exclude:` and the [default ignores](#default-ignores). |
| `--as` | `<format>` | — | Force an input [format](/docmeta/reference/formats/) (extractor name, e.g. `markdown`). Required when reading from stdin. |
| `-f, --format` | `<pretty\|json>` | `pretty` | Output format. Anything else is a usage error (exit `2`). |
| `-c, --config` | `<path>` | discovered | Path to a [config file](/docmeta/reference/configuration/). When set, the file must exist or docmeta exits 2. |
| `--no-config` | — | off | Ignore any discovered config file. `-c` and `--no-config` set the same option, so the one written later on the command line wins. |

### Reading the report

```
1,204 files scanned · 38 with no metadata block

key            coverage  types            sample
title             99.8%  string           "Getting started"
type              61.4%  string (7 enum)  guide | reference | how-to | …
owner             12.0%  string           "docs-team"
lastReviewed       3.2%  string (date)    "2026-04-01"
```

Each column answers one question:

| Column | What it tells you |
|---|---|
| **coverage** | Near 100% means you can make it `required` today. Middling means require it behind a [baseline](#baselines) ratchet. Low single digits means it is one team's convention, not a standard. |
| **types** | A distribution with counts. `string ×900, number ×4` is four data errors, not a type union — the four are listed by file and line beneath the table. |
| **sample** | What the values look like, which is what tells you whether the key means what its name suggests. |

**Files with no metadata block get their own line**, not a quieter denominator.
They pass a require-nothing schema and fail the moment any key becomes
`required`, so their count is the number you need before you ratchet.

`infer` always exits `0` when it produced a report. It has no findings and no
verdict; it is a measurement, and the decisions are yours.

### The draft schema

`--out` writes a schema that **requires nothing** and constrains only what was
observed: the dominant type per key, `minLength: 1` on a string key where no
empty value was ever seen, and an `enum` where the values are plainly a
vocabulary.

<Aside type="caution" title="`infer` never writes `required`">
Not under any flag, and there is deliberately no `--require-above <pct>`. What
your docset happens to contain is not the same thing as what your standard
should demand, and a tool that turned 61% coverage into a rule would be
laundering the status quo into policy. Promote a key into `required` yourself,
one at a time, with [`--write-baseline`](#baselines) behind it.
</Aside>

Two more rules keep the draft honest:

- **Dominant type, never a union.** A key that is a `string` in 900 files and a
  `number` in 4 gets `"type": "string"`, and the four are named in the report as
  the data errors they are. A union would encode the typo as the contract.
- **`enum` only when the values are a vocabulary.** At most 20 distinct values,
  **and** at most 5% of the files scanned. Both conditions: a 30-file repo where
  every `title` is unique passes a ratio test alone and would produce a 30-value
  `enum` for prose.

`--out` refuses to overwrite an existing file — the draft is a starting point you
then edit, and clobbering it would throw the edits away — and refuses a path
`.gitignore` covers, for the same reason [`vendor`](#schemas-vendor) does: a
generated schema you cannot commit validates on your machine and is simply
absent in CI.

Only **top-level keys** are reported. Whether `author` is present across the
docset is the standard-level question; whether `author.name` exists is a
schema-authoring detail you settle while editing the draft.

```sh
docmeta schemas infer docs/
docmeta schemas infer docs/ --min-coverage 5
docmeta schemas infer docs/ --out ./schemas/permissive.json
docmeta schemas infer docs/ -f json
```

## `schemas vendor`

Download a remote schema into this repository and pin it in config, so the
contract lives in your own history instead of depending on a host staying up.

```sh
docmeta schemas vendor <url> [options]
```

### Arguments

| Argument | Description |
|---|---|
| `<url>` | The `http(s)` URL to download. Required. |

### Options

| Option | Argument | Default | Description |
|---|---|---|---|
| `--dir` | `<path>` | `./schema` | Directory for the committed copy. Must be a path the repository tracks — see below. |
| `-c, --config` | `<path>` | discovered | Path to the [config file](/docmeta/reference/configuration/) to rewrite. |

Vendoring writes two things: the schema file itself, and a `schemas:` entry
naming it, where it came from, and the digest of the bytes that were fetched.

```yaml
schemas:
  - ref: ./schema/2.1.json
    source: https://schemas.example.com/house/2.1.json
    integrity: sha256-392da4339d91f59e3161a083a5d95913b6c7f98668e2bdfbebae53dc123e8994
```

Commit both. From then on the schema resolves from the local copy, so the run
no longer depends on the origin being reachable, and any later change to those
bytes is an [integrity failure](/docmeta/reference/schema-resolution/) rather
than a contract that shifted without anyone noticing.

<Aside type="caution" title="The target directory must be tracked">
`vendor` refuses to write into a directory `.gitignore` covers, and checks
before it downloads. An ignored copy validates on the machine that created it
and is simply absent in CI, where the failure reads as a schema nobody changed —
which is the failure vendoring exists to remove.
</Aside>

## Shared input model

`validate`, `get`, and `fill` resolve their inputs the same way.

- **Positional paths** are files, directories, or globs. A named file is always
  read. A directory or glob is expanded and filtered to the extensions in
  `--ext` (or, by default, the extensions of the [implemented
  formats](/docmeta/reference/formats/)), and then to what your repository does
  not [ignore](#gitignore).
- **`-` reads stdin.** Stdin requires `--as <format>` to choose an extractor,
  because there is no filename extension to detect from. Without `--as`, docmeta
  exits 2.
- **Config `paths:` is the fallback.** When no positional paths are given,
  docmeta uses `paths:` from the [config file](/docmeta/reference/configuration/).
  Positional paths, when present, override config `paths:` entirely.
- **No input and no config is an error.** If you pass no paths and no config
  supplies `paths:`, docmeta reports an operational error and exits 2. It does
  not silently produce empty output.
- **Matching no files is also an error.** A named path that does not exist, or
  an input set that resolves to zero files, exits 2 unless you pass
  `--allow-empty`. See [empty input sets](#empty-input-sets).

<Aside type="caution">
`--as` forces one extractor for every input in the run. Use it for stdin, or to
read a file whose extension docmeta would not otherwise recognize.
</Aside>

### Empty input sets

Resolving **zero files is an error** (exit 2), not a pass. Exit 0 means every
file passed; with no files there is no verdict, so reporting success would turn
a glob that stopped matching into a permanently green gate that checks nothing.

Two cases, both exit 2:

| Situation | Message |
|---|---|
| A named path that does not exist — `docmeta validate docs/typo.md` | `File not found: "docs/typo.md".` |
| Everything resolved, but nothing matched — `docmeta validate "docs/**/*.nomatch"` | `No files matched. Patterns tried: …` |

A named path is reported even when other inputs did match, so `docmeta validate
good.md typo.md` is an error rather than a partial success. `--ext` and
`--exclude` filters are named in the message when they were in play, because
"no files matched" is baffling when the glob plainly matches files on disk. So
is [`.gitignore`](#gitignore), which is the one filter you never wrote on the
command line:

```
No files matched. Patterns tried: "**/*.md".
Filters applied — .gitignore skipped 12 (pass --no-gitignore to check them).
```

Reading stdin with `-` is one input, so an empty piped document still produces a
verdict and is unaffected.

Pass `--allow-empty` (or set [`allowEmpty:
true`](/docmeta/reference/configuration/#keys)) when matching nothing is
expected — a shared CI template running across repos that may have no docs yet,
or a pre-commit hook whose file list can be empty.

<Aside type="note">
Because `validate` is the default command, a misspelled subcommand parses as a
path. `docmeta valdiate docs/` exits 2 with `Unknown command "valdiate". Did you
mean "validate"?`. The suggestion only fires on a token that is not a path, has
no separator, extension, or glob character, and does not exist on disk — so
`docmeta docs/` keeps working.
</Aside>

### Default ignores

Directory and glob expansion always skips these globs, in addition to anything
from `--exclude` or config `exclude:`:

| Glob | Skips |
|---|---|
| `**/node_modules/**` | Dependency directories. |
| `**/.git/**` | The Git metadata directory. |

Dotfiles and dot-directories are also excluded from directory and glob walks by
default. An explicitly named file is always read, even if it matches an ignore
glob or is a dotfile.

#### `.gitignore`

Directory and glob expansion also skips anything your repository already
ignores, so a built site (`build/`, `_site/`, `.docusaurus/`), a vendored copy,
or a local scratch directory is not validated. Generated Markdown usually has
transformed or stripped front matter, which produces violations nobody can fix
in source — and restating `.gitignore` in `exclude:` means two lists to keep in
sync.

The question is put to **git itself**, one `git check-ignore` per run, so the
answer is git's: nested `.gitignore` files, directory-only patterns, anchoring,
`.git/info/exclude`, and `core.excludesFile` all behave exactly as they do for
`git status`. Notably, a negation cannot re-include a file below an excluded
directory — with `tmp/` and then `!keep.md`, `docs/tmp/keep.md` stays ignored.

Four things bound it:

- **Explicitly named files are never filtered.** `docmeta validate
  build/generated.md` validates that file. Filtering applies only to directory
  and glob expansion, exactly like the extension filter.
- **The count is reported.** A run that skipped something says so:
  `1 file checked, 1 passed, 0 failed, 0 errors, 1 skipped by .gitignore`, and
  `json` output carries
  [`summary.gitignoreSkipped`](/docmeta/reference/output-and-exit-codes/#json).
  The count covers only files that passed the extension filter, so it answers
  "how many candidate documents did `.gitignore` take away". `--exclude`
  removals are not counted — those you asked for.
- **Outside a repository, nothing is filtered.** An extracted tarball, `npm
  pack` output, or a container with no `git` binary runs exactly as before, and
  silently. Set [`respectGitignore:
  true`](/docmeta/reference/configuration/#keys) explicitly to be told on stderr
  when filtering was asked for and could not happen.
- **`--no-gitignore` turns it off** for one run, and `respectGitignore: false`
  for a repository.

<Aside type="caution">
This makes the gate **quieter**: a repo that was validating generated files will
check fewer of them, and a run that was red can turn green. The skipped count is
what makes that auditable, and a docs tree that is ignored in its entirety fails
with `No files matched` (exit 2) rather than reporting a green zero.
</Aside>
