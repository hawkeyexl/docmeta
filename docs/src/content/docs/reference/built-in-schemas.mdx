docmeta bundles nineteen schemas. You reference any of them by id, with no file
to write, no URL to host, and no network call at validation time. This page is
the registry: what each one constrains, whether it requires anything, and which
are applied when you pass no flags at all.

Run `docmeta schemas` to print the same list from the version you have
installed.

## The published URLs

Every built-in is also served as plain JSON, at a version-pinned path under
`https://hawkeyexl.github.io/docmeta/schemas/`:

```text
https://hawkeyexl.github.io/docmeta/schemas/okf/0.1.json
https://hawkeyexl.github.io/docmeta/schemas/seven-action/1.0.json
https://hawkeyexl.github.io/docmeta/schemas/diataxis/1.0.json
https://hawkeyexl.github.io/docmeta/schemas/tgdp/1.0.json
https://hawkeyexl.github.io/docmeta/schemas/docusaurus-docs/3.10.json
https://hawkeyexl.github.io/docmeta/schemas/docusaurus-blog/3.10.json
https://hawkeyexl.github.io/docmeta/schemas/docusaurus-pages/3.10.json
https://hawkeyexl.github.io/docmeta/schemas/starlight/0.41.json
https://hawkeyexl.github.io/docmeta/schemas/antora/3.1.json
https://hawkeyexl.github.io/docmeta/schemas/sphinx/9.1.json
https://hawkeyexl.github.io/docmeta/schemas/myst/1.10.json

https://hawkeyexl.github.io/docmeta/schemas/dita/1.3.json
https://hawkeyexl.github.io/docmeta/schemas/hugo/0.165.json
https://hawkeyexl.github.io/docmeta/schemas/jekyll/4.4.json
https://hawkeyexl.github.io/docmeta/schemas/vitepress/1.6.json
https://hawkeyexl.github.io/docmeta/schemas/x-cards/1.0.json
```

They exist for three jobs: `$ref`-ing a built-in from a schema of your own,
using one with a JSON Schema tool that is not docmeta, and reading the actual
JSON instead of a description of it.

**Inside docmeta, a published URL costs nothing.** docmeta recognises its own
URLs and answers them from the copy bundled in the package — no request, no
timeout, and no dependence on GitHub Pages being up. `--offline` and an
air-gapped build work exactly as they do with the id, and a
[`schemaTrust`](/docmeta/reference/configuration/) policy that refuses URLs
still accepts these, because they reach nothing. The two spellings are
interchangeable:

```markdown
---
$schema: https://hawkeyexl.github.io/docmeta/schemas/okf/0.1.json
type: how-to
---
```

<Aside type="note" title="Each schema's `$id` is not its URL, on purpose">
Open one of the files and you will see `"$id": "google:okf:0.1"` rather than the
`https://…` address you fetched it from. Some strict JSON Schema tooling warns
about that mismatch. The warning is expected and the file is not broken.

The `$id` is docmeta's reference for the schema: it is what a document's
`$schema` names, what Ajv de-duplicates registrations on, and what appears in
every report. Changing it to the URL would move all three at once and would
break every document already carrying `$schema: google:okf:0.1`. The retrieval
URI and the identifier are simply two different names for one schema, and both
resolve.
</Aside>

### Extend a built-in with `$ref`

The reason a URL beats a copy-paste. Reference a built-in from your own schema
and add to it, by either name — the id and the URL both work, and neither
touches the network:

```json title="house.schema.json"
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "allOf": [{ "$ref": "google:okf:0.1" }],
  "required": ["title", "owner"],
  "properties": {
    "owner": { "type": "string", "minLength": 1 }
  }
}
```

Every rule the built-in carries still applies, and yours are added on top. This
is composition *inside* one schema, which is different from listing two schemas
in a set — a set applies each schema whole and attributes failures separately,
while a `$ref` lets you narrow or extend what the built-in said.

<Aside type="caution" title="A published URL never changes — that is the point">
Each of these paths is immutable. The bytes served at
`schemas/okf/0.1.json` today are the bytes served there for good; a fix to a
built-in ships as a *new* version file rather than an edit to a published one.
A CI check hashes every schema against a committed manifest and fails the build
if an already-published version is altered, so this is enforced rather than
promised.

Two hosting caveats for anything load-bearing outside docmeta: GitHub Pages can
return 404 briefly during a deploy, and its `Access-Control-Allow-Origin: *` is
current behaviour rather than a contract. If a build must not depend on either,
[vendor the file](/docmeta/reference/configuration/) into your own repository
and reference the local copy.
</Aside>

## Two kinds of built-in

The **Requires** column above is the distinction that matters when you pick one.

**Editorial schemas** describe what a page *is*. `google:okf:0.1` and the two
`type` vocabularies demand their key, because adopting them is a claim that
every page carries that classification, which makes an unclassified page a gap
rather than an abstention. Turning one on for the first time reports every page
that has not caught up yet.

**Platform schemas** describe what your site generator accepts. A platform
schema requires **exactly what the generator refuses to build without**, and
nothing more — so what it demands is a fact about the tool, not an editorial
choice docmeta made for you.

That cuts both ways. The three `docusaurus:*` schemas and `sphinx:docinfo:9.1`
require nothing, because those tools mark no field as mandatory; switching one
on cannot fail a page that was already building. `astro:starlight:0.41` and
`antora:page:3.1` both require `title`, because Starlight and Antora both
*error* without a page title — a page failing that check was already broken, and
docmeta is only telling you sooner.

Full field tables are on the [Platform
schemas](/docmeta/reference/platform-schemas/) and [Docusaurus
schemas](/docmeta/reference/docusaurus-schemas/) pages.

**Vocabulary schemas** are a third kind, and the newest. They describe a
document to something *outside* your docs site: a social card renderer
(`ogp:article:1.0`), a catalogue or repository (`dcmi:elements:1.1`), or another
publisher's build (`microsoft:learn:1.0`). Open Graph is the one built-in that
checks something no build tool checks — nothing fails when `og:image` is
missing, the page just renders badly everywhere it is shared. See [Metadata
vocabularies](/docmeta/reference/metadata-vocabularies/).

The two kinds mostly claim different keys, so they compose. One run can hold a
page to your generator's contract and to your own standard, attributing each
failure to the schema that raised it:

```bash
docmeta validate docs/ -s docusaurus:docs:3.10 -s diataxis:diataxis:1.0
```

<Aside type="caution" title="One overlap to know about: `tags`">
Stacking a Docusaurus schema with `google:okf:0.1` is the exception. Both define
`tags`, and their definitions disagree: OKF allows a list of **strings only**,
while Docusaurus also allows a tag object. Every schema in a set applies in
full, so a page using the object form fails OKF:

```text
✗ docs/install.md
    /tags/0  must be string  (line 6)  [google:okf:0.1]
```

If your docs set uses object tags, pair the Docusaurus schema with a vocabulary
(`diataxis:diataxis:1.0` or `tgdp:templates:1.0`, which claim only `type`)
rather than with OKF, or use the string form. `title` and `description` also
appear in both, and those definitions agree.
</Aside>

<Aside type="caution" title="`diataxis` and `tgdp` are alternatives, not a pair">
Both claim `type`. Stacking them is legal but narrows the accepted values to the
intersection of the two vocabularies, which is rarely what anyone wants. Pick
one. See [which ones
compose](/docmeta/reference/taxonomy-schemas/#which-ones-compose).
</Aside>

## What runs when you pass no flags

Only two of the nineteen are in the default set:

```text
google:okf:0.1 + passo-uno:seven-action:1.0
```

Everything else is opt-in. Seven-Action is safe to carry by default precisely
because it requires nothing — it rules that an `action`, if present, is
legitimate, without insisting on one. The default set sits at the bottom of the
[precedence chain](/docmeta/reference/schema-resolution/#precedence) and applies
only when no `--schema` flag, no in-file `$schema`, and no config rule matched.

## Turn one on

Three ways, in [precedence
order](/docmeta/reference/schema-resolution/#precedence) — the first one that
matches wins, and each replaces the set rather than adding to it.

<Tabs>
<TabItem label="Command line">

Repeat `-s` to build a set. This overrides everything else for the whole run:

```bash
docmeta validate docs/ -s docusaurus:docs:3.10 -s google:okf:0.1
```

</TabItem>
<TabItem label="Config file">

Set a default for the repo, and override it per directory. This is the right
place for the Docusaurus schemas, since a Docusaurus site has three content
roots with three different contracts:

```yaml title="docmeta.config.yaml"
schemas:
  - google:okf:0.1
overrides:
  - files: "docs/**"
    schemas:
      - docusaurus:docs:3.10
      - diataxis:diataxis:1.0
  - files: "blog/**"
    schemas:
      - docusaurus:blog:3.10
  - files: "src/pages/**"
    schemas:
      - docusaurus:pages:3.10
```

</TabItem>
<TabItem label="In the document">

A document can name its own schema, which beats any config rule:

```markdown
---
$schema: diataxis:diataxis:1.0
type: how-to
---
```

`$schema` also takes a list, and docmeta strips the key before validating, so it
never trips a schema that forbids unknown properties.

</TabItem>
</Tabs>

## Version ids

A built-in id is `vendor:name:version`. The version segment tracks the upstream
standard, not docmeta's own release number:

- `google:okf:0.1` is OKF v0.1.
- `docusaurus:docs:3.10` is the front matter contract of Docusaurus 3.10.
- `hugo:page:0.165` is the contract as of Hugo 0.165. Hugo releases monthly and
  its front matter fields change far more slowly, so this id is not expected to
  move every month — a new one ships when the *contract* changes, not when Hugo
  does.
Ids are stable. A new upstream version arrives as a *new* id rather than a
change to an existing one, so upgrading docmeta never silently retightens a
check you already passed. Pin the id you validated against and move it
deliberately.

## If none of these fit

The built-ins are a shortcut, not a ceiling. A docs set with its own field names
or its own vocabulary needs its own schema — a `.json` file you reference by
path, or a URL you host for several repos to share. Copying the closest built-in
and editing it is usually faster than starting from nothing.
