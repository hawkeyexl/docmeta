A `docmeta.config.yaml` file supplies default targets, excludes, the default
[schema set](/docmeta/reference/schema-resolution/), and optional per-glob overrides, so
CI can run a bare `docmeta validate`. The config is optional; every key has a
default, and docmeta runs without a config when you pass paths and schemas on
the command line.

## Keys

| Key | Type | Default | Description |
|---|---|---|---|
| `paths` | `string[]` | none | Default files, directories, or globs to process when no positional paths are given. |
| `exclude` | `string[]` | none | Globs to exclude from directory and glob walks. Merged with `--exclude` and the [default ignores](/docmeta/reference/cli/#default-ignores). |
| `schemas` | `string[]` | none | Default [schema set](/docmeta/reference/schema-resolution/) applied to every file that no higher-precedence rule matches. |
| `overrides` | `Override[]` | none | Per-glob schema overrides. The first matching entry wins. See [Overrides](#overrides). |
| `baseline` | `string` | none | Path to a [validation baseline](/docmeta/reference/cli/#baselines). Setting it turns on `--baseline` for every run; `--no-baseline` suppresses it for one. A bare `--write-baseline` records into this same file. |
| `allowEmpty` | `boolean` | `false` | Treat an input set that resolves to zero files as success instead of an error (exit 2). Equivalent to `--allow-empty`. See [empty input sets](/docmeta/reference/cli/#empty-input-sets). |
| `respectGitignore` | `boolean` | `true` | Skip files `.gitignore` covers when expanding directories and globs. `--no-gitignore` overrides it for one run. See [`.gitignore`](/docmeta/reference/cli/#gitignore). |
| `fill` | `Fill` | none | Defaults for [`docmeta fill`](/docmeta/reference/cli/#fill). See [Fill](#fill). |

The top level must be a YAML mapping. Each of `paths`, `exclude`, and `schemas`
must be a list of strings; a non-list or a list containing a non-string value is
an error (exit 2). `allowEmpty` and `respectGitignore` must be booleans — a
quoted `"false"` is a string, and accepting it would turn a setting **on** for
someone who wrote it off.

<Aside type="caution">
`allowEmpty: true` disables the check that stops a glob which stopped matching
from reporting a permanently green result. Set it only where matching nothing is
genuinely expected — a repo in a shared CI template that may have no docs yet.
</Aside>

### `respectGitignore`

Set it to `false` for a repository whose ignored files should still be checked —
a vendored docset, or a generated tree you deliberately validate:

```yaml title="docmeta.config.yaml"
respectGitignore: false
```

Setting it to `true` says the same thing as the default, with one addition: it
records that you *asked*, so a run where git could not answer — no repository,
or no `git` on `PATH` — prints one line to stderr instead of silently checking
everything. Worth doing in a CI image you do not control.

### Fill

`fill` is a mapping of defaults for the [`fill`](/docmeta/reference/cli/#fill)
command. Every key is optional, and every one is overridden by its CLI flag.

| Key | Type | Default | Description |
|---|---|---|---|
| `provider` | `string` | `auto` | Inference provider: `auto`, `anthropic`, `openai`, `claude-cli`, `llama-cpp`, or `mock`. `auto` [detects one](/docmeta/reference/cli/#fill). An unknown name is an error (exit 2). |
| `model` | `string` | provider default | Model override. Requires `provider` to be set to something other than `auto`, since a model name does not say which provider owns it (exit 2). |
| `confidenceThreshold` | `number` | `0.7` | Minimum self-reported confidence, from 0 to 1, needed to write a value. |
| `maxCostUsd` | `number` | none | Stop scheduling new files once this much has been spent. |
| `concurrency` | `number` | `4` | Files inferred in parallel. Between 1 and 64. |

A numeric key outside its range, or one that is not a finite number such as
YAML's `1e999`, is an error (exit 2).

```yaml title="docmeta.config.yaml"
fill:
  provider: anthropic
  confidenceThreshold: 0.9
  maxCostUsd: 5
```

Pinning `provider` is worth doing in CI. Left on `auto`, a runner that loses its
API key silently falls through to a local model and downloads gigabytes rather
than failing the build.

### Overrides

`overrides` is a list of mappings, each applying a schema set to files matching
a glob.

| Field | Type | Required | Description |
|---|---|---|---|
| `files` | `string` | yes | A glob matched against each file's path. |
| `schemas` | `string[]` | yes | The schema set applied to matching files. |

For a given file, docmeta uses the **first** override whose `files` glob matches
(in list order); later matching overrides are ignored. See [schema
resolution](/docmeta/reference/schema-resolution/#precedence) for where overrides sit in
the precedence chain.

## Example

```yaml
# docmeta.config.yaml
paths:
  - "docs/**/*.md"
  - "docs/**/*.mdx"
exclude:
  - "docs/drafts/**"
schemas:
  - google:okf:0.1
overrides:
  - files: "docs/api/**"
    schemas:
      - ./schemas/api.schema.json
  - files: "docs/guides/**"
    schemas:
      - ./schemas/guide.schema.json
```

## Discovery

When you do not pass `-c/--config`, docmeta searches the current working
directory and then each parent directory in turn. In every directory it looks
for these files, in order:

1. `docmeta.config.yaml`
2. `docmeta.config.yml`

The **first file found wins** and the search stops there. Configs are never
merged: `schemas` is a set every file must satisfy in full and `overrides` is
first-match-wins ordered, so a partial merge would quietly redefine what the
contract means. A `docmeta.config.yaml` inside `docs/` therefore *shadows* the
one at the repo root for runs started inside `docs/` — the escape hatch for a
subtree with genuinely different rules. For per-directory rules within one
contract, prefer [`overrides`](#overrides) instead.

The search stops at the **project boundary**: the first directory containing a
`.git` entry, which is itself searched. A git *file* — what a worktree or a
submodule carries — counts as a boundary just as a directory does. If no
ancestor is a repository, only the current working directory is searched;
docmeta never reads a config from your home directory or from `/`.

If no config is found, docmeta runs on the [built-in default schema
set](/docmeta/reference/schema-resolution/#precedence). Pass `--no-config` to
skip discovery deliberately — useful for a one-off run against the defaults.

When you pass `-c/--config <path>` explicitly, no search happens at all and that
file must exist; a missing config file is an error (exit 2).

When a run is governed by a config, docmeta says so before the report:

```
Using docmeta.config.yaml (../..)
```

The path in parentheses is the config's directory relative to where you ran the
command. The line goes to stdout in `pretty` output and to stderr for `json` and
`github`, so machine-readable output stays parseable.

## What relative paths are relative to

A config's relative paths mean what they look like they mean to whoever is
editing the config: they resolve against **the config file's own directory**,
not the directory you happened to run from. That applies to `paths`, `exclude`,
`baseline`, and any local `.json` schema file named in `schemas` or `overrides`.
So a config means the same thing whether you run from the repo root, from
`docs/`, or from a monorepo package script.

This matters most for `baseline`. Resolving it against the working directory
instead would mean a run from a subdirectory quietly found no baseline and
reported the entire recorded backlog as new. For the same reason, the schema
reference inside a [violation fingerprint](/docmeta/reference/cli/#baselines) is
measured against the config's directory too, so a baseline recorded from the
repo root matches one recorded from `docs/`, byte for byte.

Two things stay relative to the **current working directory** instead, because
a person standing in a shell typed them there:

- positional `[paths...]` on the command line, and `-s/--schema`;
- a document's own `$schema` value.

A single run uses *either* positional paths *or* config `paths`, never both, so
there is exactly one base per run. When the run takes its targets from config
`paths`, reported file paths are relative to the config's directory.

## How config merges with CLI flags

CLI flags and config values combine per setting. Some flags override the
corresponding config value; others merge with it.

| Setting | CLI flag | Config key | How they combine |
|---|---|---|---|
| Inputs | `[paths...]` | `paths` | CLI positional paths **override** config `paths` entirely. Config `paths` is used only when no positional paths are given. |
| Excludes | `--exclude` | `exclude` | **Merged.** The effective exclude set is config `exclude` plus every `--exclude` glob plus the [default ignores](/docmeta/reference/cli/#default-ignores). |
| Schemas | `-s/--schema` | `schemas` / `overrides` | CLI `--schema` **overrides** both `schemas` and `overrides` for every file. See [precedence](/docmeta/reference/schema-resolution/#precedence). |
| Config discovery | `--no-config` | — | `--no-config` skips discovery entirely, so no config value applies. It sets the same option as `-c/--config`, so if you pass both, whichever comes later on the command line wins. |
| Empty input sets | `--allow-empty` | `allowEmpty` | The flag **overrides** the config key, and only in the permissive direction: passing it turns the check off. Omitting it falls back to config, then to off. |
| Fill settings | `--confidence`, `--provider`, `--model`, `--max-cost-usd`, `--concurrency` | `fill.*` | Each flag **overrides** its matching `fill` key. An unset flag falls back to config, then to the built-in default. |

<Aside type="caution">
`--schema` is all-or-nothing: passing it once makes that schema set apply to
**every** file in the run, bypassing config `overrides` and per-file `$schema`.
Use config `overrides` when different folders need different schemas.
</Aside>
