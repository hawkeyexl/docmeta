docmeta ships three **taxonomy** schemas: closed vocabularies that constrain a
classification field to a published set of values. They exist because
[`google:okf:0.1`](/docmeta/reference/okf-schema/) requires a `type` but accepts
any non-empty string for it, so it cannot stop a docs set from drifting into
`how-to`, `howto`, and `guide` all meaning the same thing.

| Id | Key | Key required? | Framework |
|---|---|---|---|
| `diataxis:diataxis:1.0` | `type` | No | [Diátaxis](https://diataxis.fr/) |
| `tgdp:templates:1.0` | `type` | **Yes** | [The Good Docs Project](https://www.thegooddocsproject.dev/template) |
| `passo-uno:seven-action:1.0` | `action` | No | [Seven-Action Documentation Model](https://passo.uno/seven-action-model/) |

All three use [Draft 2020-12](/docmeta/reference/schema-resolution/#dialects),
allow additional properties, and are [built-in
references](/docmeta/reference/schema-resolution/#reference-kinds).

The two keyed on `type` are alternatives to each other — see [Which ones
compose](#which-ones-compose).

## Vocabulary checks vs. presence checks

Two of the three check a value only *if one is present*. A document with no
`type` at all passes `diataxis:diataxis:1.0`, because that schema's job is to
rule that a type, if given, is legitimate — not to insist on one.

That is deliberate: it makes them safe to layer onto an existing setup, and it
keeps "must have a type" as a separate decision from "which types exist."
To get both, stack a vocabulary schema with one that requires the field:

```bash
docmeta validate docs/ -s google:okf:0.1 -s diataxis:diataxis:1.0
```

OKF supplies the requirement, Diátaxis supplies the vocabulary.

`tgdp:templates:1.0` is the exception: it **requires** `type` as well as
constraining it, so it needs no partner to get presence-checking. Adopting a
named template set is a stronger claim than adopting a vocabulary — it says
every page *is* one of the templates, which makes an untyped page a gap rather
than an abstention. Pair it with OKF for the other OKF fields, not for `type`.

## `diataxis:diataxis:1.0`

Constrains `type` to the four Diátaxis forms.

| Value | Orientation |
|---|---|
| `tutorial` | Learning-oriented |
| `how-to` | Task-oriented |
| `reference` | Information-oriented |
| `explanation` | Understanding-oriented |

```md
---
type: how-to
title: Rotate an API key
---
```

Diátaxis is **not** part of the [default
set](/docmeta/reference/schema-resolution/#precedence). It constrains `type`,
which documents already carry, so applying it by default would fail every repo
not already using Diátaxis. Opt in with `-s` or a `schemas:` entry in config.

## `tgdp:templates:1.0`

Requires `type` and constrains it to the template slugs published by [The Good
Docs Project](https://www.thegooddocsproject.dev/template). Where Diátaxis names
four abstract forms, TGDP names 25 concrete deliverables, so it fits a docs set
that thinks in terms of "we owe this product an installation guide and a
changelog" rather than in terms of the four quadrants.

The values are the template directory slugs from the upstream
[templates repo](https://gitlab.com/tgdp/templates), grouped here by the pack
each belongs to. All 25 validate regardless of pack; the grouping is upstream's,
and is reproduced only to show what you are opting into.

| Pack | Values |
|---|---|
| Core | `concept`, `how-to`, `readme`, `reference`, `release-notes`, `troubleshooting`, `tutorial` |
| Community | `bug-report`, `changelog`, `code-of-conduct`, `code-of-conduct-incident-record`, `code-of-conduct-remediation-record`, `code-of-conduct-response-plan`, `contributing-guide`, `our-team` |
| Misc | `api-getting-started`, `api-reference`, `contact-support`, `glossary`, `installation-guide`, `quickstart`, `sdk-overview`, `style-guide`, `terminology-system`, `user-personas` |

```md
---
type: installation-guide
title: Install the collector
---
```

A document with no `type` fails against this schema:

```text
✗ docs/overview.md
    (root)  must have required property 'type'  (line 1)  [tgdp:templates:1.0]
```

Like Diátaxis, TGDP is **not** in the [default
set](/docmeta/reference/schema-resolution/#precedence), and even more plainly:
it both constrains and requires `type`, so defaulting it would fail every
untyped document in every repo that had not opted in.

<Aside type="caution" title="It requires `type`, so retrofit with `--dry-run` first">
This is the only taxonomy schema that fails a document for *lacking* its key. On
an existing docs set that never adopted TGDP, turning it on reports every
untyped page at once. Run [`docmeta fill
--dry-run`](/docmeta/reference/cli/#fill) to see what would be proposed before
writing anything — the enum is lifted into the inference prompt, so the model is
constrained to a real slug.
</Aside>

<Aside type="note" title="TGDP prescribes no frontmatter of its own">
The upstream templates are body-structure templates — they open at a heading and
carry no YAML block. The only metadata TGDP publishes is `index.json`, which
describes the *templates* (`name`, `summary`, `last_updated`, `contributors`,
`packs`), not documents written from them. So the vocabulary here is lifted from
the template set, not an implementation of a TGDP metadata spec, and requiring
`type` is docmeta's choice rather than an upstream rule. Pair it with
[`google:okf:0.1`](/docmeta/reference/okf-schema/) for the fields TGDP leaves
unspecified.
</Aside>

## `passo-uno:seven-action:1.0`

Constrains `action` to the seven reader actions. Derived from upstream model
version `2025-01-09`.

| Value | Alternate verb | What the reader is doing |
|---|---|---|
| `appraise` | Discern | Judging whether something fits their situation |
| `understand` | Learn | Grasping a concept |
| `explore` | Discover | Finding out what exists |
| `practice` | Train | Building a skill by doing |
| `remember` | Recall | Looking up a detail they once knew |
| `develop` | Integrate | Building the thing into their own work |
| `troubleshoot` | Solve | Getting past a problem |

Only the left column validates. The alternate verbs are how the model names each
action in prose; `action: learn` fails.

```md
---
action: practice
title: Work through the tutorial
---
```

This schema **is** in the default set, alongside OKF. It can be, because it
constrains a key that documents do not otherwise carry and does not require it —
so it fails nothing that passed before.

<Aside type="caution" title="If you already use an `action` key">
`action` is a generic field name. If your frontmatter already uses it for
something else (a workflow name, a button label), two things change:

- **`validate` fails.** Your value is not in the vocabulary, so it is reported
  as an error against `passo-uno:seven-action:1.0`.
- **`fill` overwrites it.** A key whose value is invalid is a candidate for
  *replacement*, not just for filling a gap, and `docmeta fill` writes to disk
  unless you pass `--dry-run`. Run `docmeta fill --dry-run` first on any repo
  that uses `action` for something of its own.

Set a `schemas:` list in `docmeta.config.yaml` before running either command.
It replaces the default set entirely, which opts you out of both.
</Aside>

## Which ones compose

Diátaxis and TGDP both classify what a page **is**, so both claim `type`.
Seven-Action classifies what a reader is **doing**, which is independent, so it
claims `action` and composes with either:

```md
---
type: how-to
action: practice
title: Rotate an API key
---
```

| Combination | Result |
|---|---|
| Diátaxis + Seven-Action | Composes |
| TGDP + Seven-Action | Composes |
| Diátaxis + TGDP | **Pick one** |

Stacking the two `type` schemas is not an error, but it validates against the
intersection of their vocabularies, which is narrower than either. `explanation`
is Diátaxis-only and `installation-guide` is TGDP-only, so each rules out values
the other exists to allow — leaving only `tutorial`, `how-to`, and `reference`.
Because TGDP also requires the key, the stacked pair rejects an untyped document
outright. Choose the vocabulary your docs set actually uses.

## Crosswalk

The Seven-Action model publishes a mapping to Diátaxis. It is not one-to-one:
`explore` lands on Tutorial, and Diátaxis's single how-to form splits across
three actions.

| `action` | Diátaxis `type` |
|---|---|
| `appraise` | no direct equivalent (closest: `explanation`) |
| `understand` | `explanation` |
| `explore` | `tutorial` |
| `practice` | `how-to` |
| `remember` | `reference` |
| `develop` | `how-to` |
| `troubleshoot` | `how-to` (problem-oriented) |

Use it to sanity-check a pairing, not as a rule docmeta enforces. The two
schemas validate independently; no combination of a valid `type` and a valid
`action` is rejected.

## If your vocabulary differs

The enums are strict and carry no aliases, so `howto` and `How-To Guide` both
fail. That is the point of a vocabulary check, but it means a docs set with its
own conventions needs its own schema. Copy the shape into a local file and edit
the `enum`:

```json title="schemas/types.schema.json"
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": true,
  "properties": {
    "type": {
      "type": "string",
      "enum": ["tutorial", "how-to", "howto", "reference", "explanation"]
    }
  }
}
```

Then reference it by path instead of the built-in id. See [Author a
schema](/docmeta/schemas/) for the full authoring guide.
