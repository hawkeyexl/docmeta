The terms below are defined as moose-meta uses them. Where a concept has a fuller
reference page, the entry links to it.

## frontmatter

A block of metadata at the very top of a document, set off from the body.
Markdown, MDX, AsciiDoc, and reStructuredText all accept the same fenced block in
any of three flavors: YAML (`---`), TOML (`+++`), or JSON (`;;;`). AsciiDoc and
rst fall back to a native header (AsciiDoc attributes, an RST field list) when no
fence is present, and XML and HTML have no fenced form (their metadata lives in
element attributes or head tags). A fenced block must be the first thing in the
file, or moose-meta won't recognize it. Whichever flavor or format is used, moose-meta
reads only the frontmatter, never the body, and normalizes it to the same
[metadata](#metadata) shape it validates. See
[Supported formats](/moose-meta/reference/formats/#frontmatter-flavors) for the
fence flavors and where each format keeps its frontmatter.

## metadata

The key/value pairs moose-meta validates: `type`, `title`, `timestamp`, and so on.
Metadata is what an [extractor](#extractor) pulls out of a document's
[frontmatter](#frontmatter); everything in moose-meta after extraction operates on
this generic key/value shape, regardless of the original format. moose-meta checks
the **presence and format** of metadata, never the document's prose.

## extractor

The format-specific component that reads metadata out of a document. moose-meta has
one extractor per input format: Markdown, MDX, AsciiDoc, reStructuredText, XML,
and HTML. The extractor is the only part of moose-meta that knows about a file's
format; once it produces metadata, validation and reporting work the same for
every format. You can force a specific extractor with `--as`, which is required
when reading from stdin. See [Supported formats](/moose-meta/reference/formats/).

## schema

A [JSON Schema](https://json-schema.org/) document that declares which metadata
fields are required, which are optional, and what shape each value must take.
moose-meta validates a file's metadata against one or more schemas. A schema can be
shipped with moose-meta (a [builtin](#schema-reference)), a local file, or a remote
URL.

## schema set

The one-or-more schemas resolved for a single file. moose-meta resolves a schema
**set** per file, then validates the file's metadata against **every** schema in
it. A file passes only when it satisfies all schemas in its set, and each
reported error is tagged with the schema that produced it. See
[Schema resolution](/moose-meta/reference/schema-resolution/#validating-against-the-whole-set).

## schema reference

A pointer to a schema: what appears in a `--schema` flag, a document's
[`$schema`](#schema-document-key) key, or config. moose-meta classifies each
reference into one of three kinds by its shape:

- **builtin**: a `vendor:name:version` id such as `google:okf:0.1`, resolved to
  a schema shipped with moose-meta.
- **file**: a `.json` path or any path with a separator, such as
  `./my.schema.json`, resolved from the local filesystem.
- **url**: an `http://` or `https://` URL, fetched over the network.

See [Reference kinds](/moose-meta/reference/schema-resolution/#reference-kinds).

## `$schema` (document key)

A reserved key a document can put in its own metadata to name the schema(s) it
should be validated against, as a single reference or a list. Because it's a
moose-meta directive rather than real metadata, `$schema` is **stripped before
validation**, so a schema with `additionalProperties: false` won't flag it. In
the [precedence chain](#override) it sits above config but below a `--schema`
flag. See [The `$schema` key in a file](/moose-meta/reference/schema-resolution/#the-schema-key-in-a-file).

## `$schema` (meta-schema URI)

A different use of the same key, found **inside a schema** rather than a document.
There, `$schema` is the meta-schema URI that declares the schema's
[dialect](#dialect), for example
`https://json-schema.org/draft/2020-12/schema`. moose-meta reads it to decide which
validator to compile the schema with. Don't confuse it with the document
[`$schema`](#schema-document-key) above: one selects a dialect, the other selects
which schema validates a document.

## dialect

A version of the JSON Schema specification: Draft 2020-12, 2019-09, draft-07,
draft-06, or draft-04. moose-meta auto-detects a schema's dialect from its
[`$schema` meta-schema URI](#schema-meta-schema-uri) and compiles it with the matching
validator; a missing or unrecognized URI falls back to Draft 2020-12. Schemas of
different dialects can coexist in one run. See [Dialects](/moose-meta/reference/schema-resolution/#dialects).

## JSON Pointer

The standard ([RFC 6901](https://datatracker.ietf.org/doc/html/rfc6901)) syntax
moose-meta uses to name the field an error is about. A pointer like `/tags/0` means
"the first item of the `tags` array"; an empty pointer (shown as `(root)` in
pretty output) means the document as a whole, most often a required field that's
missing entirely. Pointers appear in error output and in the `instancePath` field
of JSON output.

## OKF

The Open Knowledge Format, whose v0.1 schema (`google:okf:0.1`) ships with
moose-meta as the built-in default. OKF requires only `type` and treats every other
field (`title`, `description`, `resource`, `tags`, `timestamp`) as recommended,
tolerating unknown keys. It's what validates your files when nothing else is
configured. See [the built-in OKF schema](/moose-meta/reference/okf-schema/).

## override

In moose-meta, "override" has two related senses:

- A config **`overrides`** entry assigns a schema set to files matching a glob, so
  different folders can use different schemas. See
  [Apply different schemas to different folders](/moose-meta/set-up/different-schemas-per-folder/).
- More broadly, schema resolution is a chain of overrides: a `--schema` flag
  overrides a document's [`$schema`](#schema-document-key), which overrides config
  `overrides`, which overrides config `schemas`, which overrides the built-in
  default. The first source that yields a schema wins. See
  [Precedence](/moose-meta/reference/schema-resolution/#precedence).

## validation vs. extraction

Two distinct operations, exposed as two commands. **Extraction** reads metadata
out of a document. The `get` command prints named field values and validates
nothing. **Validation** checks that extracted metadata satisfies its
[schema set](#schema-set). That is the `validate` command, the one CI gates on. Every
validation begins with an extraction, but you can extract without validating. See
the [CLI reference](/moose-meta/reference/cli/).
